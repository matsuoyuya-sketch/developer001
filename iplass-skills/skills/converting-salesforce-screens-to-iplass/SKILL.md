# SF独自画面のiPLAssへの移植

Salesforceの独自画面をiPLAssへ移植するときの、移植可否の判定・段階分け・移植先の構成・SFロジックの写し方を扱う。移植元は**LWC(＋Apexコントローラ)**と**画面フロー(screen flow)**の2種類があり、判定と移植先の構成は共通で、移植元の読み方と写し方が違う(フローは§7)。

Entityの移行は [converting-salesforce-to-iplass-entity](../converting-salesforce-to-iplass-entity/SKILL.md) が担う。本スキルは**画面**のみを扱い、データ構造には触れない。定義の取得・投入の作法は [iplass-definition-io](../iplass-definition-io/SKILL.md) が定義位置。iPLAss側のJSON形状は `iplass-dev` プラグインのスキルを引く。環境固有の値は [CLAUDE.md](../../../CLAUDE.md) の固有値表にある。

## 1. 宣言的画面で置き換えられるかの判定

移植前に、iPLAssの宣言的画面(GEM / MDC)だけで足りるかを判定する。次のどれかがあればカスタム画面が必要になる。

| 兆候 | 理由 |
|---|---|
| 任意の深さの階層描画(自分自身をネストする子コンポーネント) | 宣言的画面は項目をセクションに並べるモデルで、木構造を描けない |
| ドラッグ&ドロップ・上下移動など画面上での直接操作と一括保存 | 1レコード単位の編集しか表現できない |
| 画面上での多段集計(配下データを横断した合計・比率) | 集計は定義済みの軸に限られる |
| 同一画面でのモード切替(期間・表示単位・編集/承認) | 画面の状態を持てない |
| ログインユーザーの役割による表示分岐 | 権限定義で表現できない業務ロジックの判定を含む |
| 独自モーダル・DOMの画像化 | 宣言的画面の枠外 |

判定に読むファイルは次の4つに絞る。全量を読む必要はない。

| 読むもの | 見るところ |
|---|---|
| LWCの `.html` | 子コンポーネントの参照、繰り返しと条件分岐、モーダルの呼び出し |
| LWCの `.js` | getterの数(=画面で計算している量)、importしている外部リソースと共通モジュール |
| Apexコントローラ | `@AuraEnabled` メソッドの一覧(=必要なサーバー処理の単位) |
| 同フォルダの子コンポーネント | ファイルサイズ(=移植量の見積り) |

**判定の結論は「全部カスタム」か「全部宣言的」の二択にしない。** データは Entity として宣言的画面の管理下に置き、画面だけカスタムにするのが既定。

移植元が**画面フロー(screen flow)**の場合、読むファイルと写し方が変わる(§7)。判定の観点そのものは上の表と同じで、フローが持つ画面の数・分岐・レコード作成の連鎖を数えて量を見積もる。

## 2. 段階分けの決め方

移植は一度に終わらせず、依存の浅い順に分ける。

| 原則 | 内容 |
|---|---|
| 第1弾は単一Entityで成立する閲覧のみ | 参照先・添付・集計元に依存する機能を含めない |
| 技術的に未検証な核を第1弾に入れる | 描画方式と画面への埋め込みを最初に通す。ここが通れば残りは量の問題になる |
| 編集・保存は後回し | 一括更新のトランザクション設計が要る。閲覧が固まる前に着手すると手戻る |
| 各弾で「やらないこと」を明示する | 積み残しを暗黙にしない |

**着手前に、画面が読み書きするEntityが移行先に存在するかを確認する。** 存在しなければ画面の設計を進めても投入できないので、Entityの移行が先行する前提として保留に起こす(置き場は [coordinating-migration-work](../coordinating-migration-work/SKILL.md))。存在する場合は、画面が表示する数値がどう移行されているかを確認する(§5)。表示できない数値があると弾の切り方が変わる。移行元の項目メタデータだけで設計を先に進めることはできるが、**そのつもりで進めたことを明示する**(移行先の型と食い違う可能性が残る)。

## 3. 移植先の構成

Javaのビルド環境を必要としない構成にする。定義の登録だけで動く。

| 層 | 使うもの | 責務 |
|---|---|---|
| サーバー | `ScriptingCommandDefinition`(Groovy) | データ取得・木構造化・並び替え |
| API | `WebApiDefinition` | Commandの公開。参照のみなら `GET` |
| 画面 | 独立したURLで開くなら **`ActionMapping` + テンプレート定義**(§4.4)、詳細画面に埋め込むなら **テンプレートセクション + Vue SFC**(§4.1) | 状態・描画・操作。実装はテンプレート定義側に置く |
| 画面(補助) | スクリプトセクション(§4.2) | 開いているレコードのoidを画面へ渡す。それ以外の実装は置かない |

**画面の幅を使う画面は単独ページを選ぶ。** 詳細画面のモーダルは狭く、MDCのヘッダ・操作バー・セクションの枠が付く。単独ページならMDCの画面部品に依存せず、借りるのはVueアプリを作る関数だけになる。逆に、埋め込みが要件なら§4.1を選ぶ。**両方に出す必要がなければ実装は1つに寄せる**(2つの経路はVueの書き方が違うため、同じコードを共有できない)。

**集計はクライアント側に置く。** サーバーは取得と並び替えに専念する。理由は3つ。

- SF側のLWCも同じ切り方をしており、対応が追いやすい
- 編集機能を載せたとき、画面上で即時に再計算できる
- Entity定義の数式Expression化(保留解除)が不要なままになる

CSS/JSの正本はファイルに置き、生成スクリプトで定義へ埋め込む。定義側を直接編集しない。**繰り返し生成する画面の正本は `scripts/` 側（Git管理）に置く**（`work/` はGit管理外で、消えると実装を復元できない）。一度きりの調査・採寸に使うものは `work/` でよい。

**Commandを書くときは、同種の動いているCommandを1つ取得して呼び出しの形を写す**(検索APIの署名・結果の返し方はスキルの記憶で埋めない)。結果は `request.setAttribute(<名前>, <MapやList>)` で返し、WebApi定義の `responseResults` に同じ名前を並べる。GroovyのMap/ListはそのままJSONへ直列化されるので、JSONを組み立てるライブラリは要らない(`groovy.json` はimportした時点で落ちる。[iplass-definition-io](../iplass-definition-io/SKILL.md) §4)。

**Commandの `script` を直しても、WebApi定義を作り直すまで古い版が走る。** WebApiは紐づくCommandを抱え込む（`newInstancePerRequest` が `false`）ため、Commandを `put` しただけでは反映されない。`get` で引き戻すと新しい `script` が入って見えるので、定義APIの応答では気づけない。**「Commandを `put` → WebApiを `delete`＋`post` → 叩く」を1本のスクリプトで回す**。これを知らないと「直したのに直らない」と「壊したはずのない名前で500」が同時に起き、名前の衝突のような見当違いの原因へ流れる。

**`responseResults` のキーを1つもsetしないと、本文が空のHTTP 500になる。** 例外を投げていなくても同じ。したがって**スクリプトの先頭で既定値を `setAttribute` し、本体全体を `try` で囲んで例外の文字列を本文へ出す**。囲まないと、原因の分からない500と「反映されていない」が区別できない。
**値が `null` のエントリは、応答からキーごと落ちる。** Mapに入れたキーが必ず応答に現れると考えて画面を書くと、`undefined` を踏む。画面側は**「キーが無い＝null」**として扱う。応答の形を約束するときも「この項目は必ず文字列」と書かない(nullになり得るなら、なり得ると書く)。

**クラス名・メソッド名・パッケージは、書く前に `iplass-dev` プラグインのスキルを引く。** 記憶で書くと**原因の見えない500**(`System error occurred.`)になり、本文からは何も分からない。実際に踏んだもの。

| 用途 | 正しい形 | 記憶で書きがちな誤り |
|---|---|---|
| 保存時の検証エラーの一覧 | `EntityValidationException#getValidateResults()` | `getErrors()`(**実在しない**) |
| 同名の `final` 変数を二重に宣言しない | 宣言は1箇所だけにする（生成で本文を組むときは**同名の `final` 宣言が無いかを機械で検査する**） | 二重宣言は**応答が空のHTTP 500**になる。他の500と違いXMLの本文すら返らないため、原因が本文から何も分からない |
| 日付項目の比較の値 | `java.sql.Date`（`new java.sql.Date(System.currentTimeMillis())`） | `new java.util.Date()`。**サーバ内部で `type is null` のNullPointerExceptionになり、原因の見えない500になる**（条件の組み立て自体は通る） |
| 前方一致の検索条件 | `condition.predicate.Like` の `new Like(項目, 値, Like.MatchPattern.PREFIX)` | `condition.expr.Like`(この環境に**無い**) / `Like.Mode.PREFIX`(**無い**) |
| Select型プロパティへの設定 | `setValue(<項目>, new SelectValue(<値>))` | 文字列をそのまま `setValue`(型が違い**500**になる) |
| Select型プロパティの取り出し | `SelectValue#getValue()` で格納値だけを返す | そのまま文字列化(画面へ `{"value":..,"displayName":..}` が出る) |

**一致方式は列挙で渡す。パターン文字列を自分で組まない。** `new Like(項目, 値 + '%')` の形は通ってしまうが、値に含まれる `%` と `_` がワイルドカードとして効き、前方一致が広域一致に化ける(`サ%ル` が「サを含みルを含む」になる)。列挙を渡せばフレームワーク側でエスケープされる。**空判定に `trim()` を使うなら、条件へ渡す値も同じtrim済みの値にする**(空判定だけtrimすると、前後に空白のある入力が「空でない」と判定されたまま一致しなくなる)。

**未検証のAPIを実機で探るときは、候補を2つだけ用意して片方の失敗をもう片方の証明にしない。** 順序は**①`iplass-dev` のスキルを引く → ②それでも分からなければ探る**。①を飛ばして②から始めると、通る形を見つけた時点で満足して**通るが間違っている形**(上のワイルドカードの例)を投入する。スキルの記載がこの環境と食い違うこともある(`iplass-query` の `patterns.md` は `expr.Like` を挙げているが、この環境には無い)ので、**引いた結果も実機で確かめる**。

**「無いときはnull」を前提にすると、無いときだけ生の500になる取得APIがある。** `load` は対象が無ければnullを返すが、**`loadAndLock` は存在しないoidで `EntityConcurrentUpdateException`（`The data subject has already been deleted.`）を投げる**。null判定だけを書くとその分岐が死に、画面には「500」しか出ない（応答はXMLで返るためJSONとしても読めない）。ロックを取って読む経路は try/catch で囲み、捕まえたら「見つからない」として扱う。

**表示名の在処はEntityによって違う。** SFの標準Nameを独自プロパティへ移したEntityは `namePropertyName` が指す宣言プロパティ(`Name`)に表示名を持ち、**`getName()`(システムの `name`)は空になる**。一方で参照プロパティから取れるEntityは名前だけを持つスタブで、宣言プロパティを持たないため `getValue('Name')` が null になる。両方に対応する。

```groovy
String dispName(Entity e) {
    if (e == null) return null
    Object v = e.getValue('Name')      // 独自Nameを持つEntity
    if (v != null) return String.valueOf(v)
    return e.getName()                  // システムのname / 参照先のスタブ
}
```

同じ理由で、**必須の `Name` を埋めるのは `setValue('Name', ...)`** である。`setName()` はシステムの `name` を設定するもので、宣言プロパティ側の `NotNullValidation` は満たせない(保存が「Input is required」で失敗する)。

## 4. MDC詳細画面への埋め込み

業務画面が宣言的画面のうちMDC系である場合、埋め込み先は詳細画面の定義になる。定義のパスと一覧取得の可否は [iplass-definition-io](../iplass-definition-io/SKILL.md) §7 が定義位置。

**詳細画面に埋め込むなら、テンプレートセクション + Vue SFC（§4.1）で作る。** スクリプトセクション（§4.2）はoidの受け渡しに限り、実装は置かない。View定義に実装を抱えさせない・状態と描画をVueに任せる・実装をテンプレート定義として単独で差し替えられる、の3点で有利になる。独立したURLで開く画面は§4.4。

### 4.1 テンプレートセクション + Vue SFC（既定）

| 要素 | 内容 |
|---|---|
| セクション | `@class` を `...element.section.MdcDetailTemplateSection` にし、`templateName` で参照先を指定する。`templateInterpretType` は `VUE_SFC` |
| 参照先 | `HtmlTemplateDefinition`（`/template/{定義名}`）の `source` にSFCを書く。`contentType` に `Content-Type: text/html; charset=UTF-8` を指定する |
| 使えるもの | `<template>` / `<script setup>` / `<style>` の3ブロック。`import { ref, reactive, computed, h, onMounted } from 'vue'` が通り、`v-for` / `v-if` / `v-model` / `@click` も動く |
| 1ファイルでの再帰描画 | 階層を再帰的に描くコンポーネントは、描画関数（`h()`）で自分自身を参照する形にすれば1ファイルに収まる |

**このセクションのVueへは、開いているレコードのoidが渡らない。** propsは `contextMap` だけで中身は空、UIコンポーネントのカタログを持つグローバルにもデータは無い。**oidを渡すだけのスクリプトセクションを併置し、`window` 経由でVueへ渡す**（oidが取れるのはGroovyTemplateが動く側だけ）。

**SFCに書けない文字列**: `<style>` や `<script>` の閉じタグを文字列リテラルに含めるとブロックが途中で閉じる。タグ名を分割して組み立てる。CSSを別ファイルで管理する場合は、生成時に `<style>` ブロックとして結合すると正本が1つで済む。

### 4.1.1 画面に重ねるパネル(モーダル)の高さ

mdcの画面は**上下に固定バーを持つ**ため、`position: fixed` で重ねたパネルは上端がヘッダーに、下端がフッターに隠れる。**高さの指定を1つ間違えるだけで、ボタンが押せない画面ができる。**

**パネルの高さは可視領域に対する割合で抑え、中央揃えにする。**

```css
.dialog { max-height: 80%; margin: auto; }   /* 上下に必ず10%ずつ空く */
```

`max-height: 100%` や `calc(100% - 24px)` は避ける。**中身が伸びると自由空間が無くなり、`margin: auto` の中央揃えが効かなくなって両端が帯の下に潜る**。中身が少ないうちは成立するので、**項目数が増える変更で初めて現れる**。

| やってはいけないこと | なぜ |
|---|---|
| 上下の余白を決め打ちする(`padding-bottom: 140px` 等) | 帯の高さは埋め込み先の都合で決まる。下を避ければ上で隠れ、上を避ければ下で隠れる |
| 固定バーの高さを実行時に測って余白にする | 全画面のモーダルが `position: fixed` で存在するため「上端に接する要素の下端」を測ると**画面の高さを拾う**。逆にバーが `fixed`/`sticky` でなければ**何も拾えず両側0**になる。どちらも症状が同じなので、測れたつもりで次の手を打つと外し続ける |
| `z-index` を上げて手前に出す | 相手のヘッダー・フッターを覆い、埋め込み先の操作を妨げる。**重ねずに避ける** |

**見え方の不具合は、画面を見られる人に数値を聞くのが最短。** ヘッダーとフッターの高さの2つが分かれば確定する。それが得られない状況では、**原因を特定しに行かず、外部要因に左右されない形(上の割合指定)へ寄せる**。

縦並びflexで中身をスクロールさせるときは、スクロールする子に **`min-height: 0`** を付ける(既定の `min-height: auto` では内容より小さくならず、`overflow: auto` が効かないまま**兄弟のフッタが枠外へ押し出される**)。ヘッダ・フッタ側には `flex: 0 0 auto` を付ける。

**投入前に3点を機械で確かめる**（実行時エラーは画面が空になるだけで原因が見えない）。

| 検査 | 何を防ぐか |
|---|---|
| `<template>` のタグ開閉の対応 | レイアウト崩れ |
| `<script setup>` がJSとしてパースできるか | 構文エラー |
| templateが参照する識別子がscriptで定義されているか | 未定義参照（定義前の使用を含む） |

### 4.1.2 入力部品の見た目

埋め込み先の画面は入力部品の枠やブラウザ標準の装飾を消していることがある。**見た目はセクションの中で完結させる**(埋め込み先のCSSクラスに乗る形は採らない)。

| 症状 | 手当て |
|---|---|
| テキスト欄・複数行入力の枠が背景と同化して境目が分からない | 枠・角丸・背景色・`padding`を自分で指定する |
| プルダウンに枠も矢印も出ず、選ぶ欄だと分からない | `appearance: none`で標準の矢印を確実に消し、矢印をSVGの`background-image`で置く。右の`padding`を矢印の分だけ広げる |
| 未選択のプルダウンが空欄で、選ぶものが無いように見える | 値が空文字の選択肢にラベルを付ける(**選び直して未選択に戻す先**にもなるので、選択肢そのものは消さない) |

**埋め込み先のCSSクラスを当てにしない。** mdcの認証画面はBootstrapを読み込み、iPLAssがそのフォーム用クラス(`.form-select`・`.form-control`)の枠色を上書きしているが、**業務画面が同じCSSを読み込んでいるとは限らない**。認証画面の`<link>`から見つけたクラスを埋め込みへ持ち込むと、枠も矢印も出ない画面になる。§4.1.1 と同じく、外部要因に左右されない形へ寄せる。

**自分のセレクタは埋め込み先の単一クラスより強い。** `.field select`(クラス＋要素)は`.form-select`(クラス1つ)に勝つため、**埋め込み先へ任せたい部分を書くとその見た目を潰す**。任せるなら書かない、描くなら全部描く、のどちらかに寄せる。

矢印のようなdata URIは、投入経路で潰れると画面だけが壊れて原因が見えない。投入後にliveを取り、原形が保たれているかを見る(作法は [iplass-definition-io](../iplass-definition-io/SKILL.md) §9)。

### 4.1.3 機能を起動するボタンには必ずアイコンを付ける

移した機能は詳細画面のタイトル領域のボタン（`detailView.topAreaButtons` の
`MdcDetailTopAreaButton`、`type` は `CUSTOM_BUTTON`）から起動する。**画面をスクロールすると
タイトル領域が縮んでボタンのラベルが隠れる**ので、`iconTag` にMDIのアイコン名を入れる。

| 事項 | 内容 |
|---|---|
| キー | `iconTag`（ボタン直下。`displayLabel` の隣に置かれる） |
| 値 | **MDIのアイコン名**（`mdi-send` 等）。アプリバーの項目と同じ規則で、綴りを誤ると**投入は通るのにアイコンが出ない** |
| 確かめ方 | 投入して取得し、`iconTag` が残っているかを見る（未知のキーは400にならず黙って落ちる） |

投入は**その時点のliveへ `iconTag` だけを足す**形にする（Viewは他の作業と共有するため）。
足したキー以外に差分が無いことを機械で照合する。定義位置は `work/report/set-button-icons.js`。

### 4.2 スクリプトセクション

oidをVueへ渡すために1つ併置する。GroovyTemplateが動くのはこちらだけなので、`request.getParam('oid')` で取り出して `window` のオブジェクトへ入れる。ラベルを空にすれば画面上でほとんど目立たない。

| フィールド | 内容 |
|---|---|
| `@class` | `org.iplass.mtp.mdc.view.entityview.detail.definition.element.section.MdcDetailScriptSection` |
| `script` | GroovyTemplate本文 |
| `templateInterpretType` | `HTML` |
| `displayView` / `displayCreate` / `displayUpdate` | 出す画面の選択。参照専用なら `displayView` のみ |

Vueを使わない小さな埋め込み（静的な表示だけ等）をこのセクションに直接書くこともできる。その場合の規則は次のとおり。

| 事項 | 規則 |
|---|---|
| `<script>` タグ | `HTML` 解釈でも実行される。CSS・JSはインライン同梱で足りる |
| 書けない記法 | 改行のエスケープ（バックスラッシュ+n）・`${`・`<% %>`・`</script`。前者は埋め込み経路で実際の改行に変換され、文字列リテラルが壊れる。**投入前に機械で検査する** |
| 壊れたときの症状 | スクリプト全体が読み込まれず、画面は初期表示のまま何も起きない。コンソールには「DOMの差し替えに失敗した」という形のエラーだけが出て原因の行は分からない。起動側に「本体が未定義のとき」「例外が出たとき」を画面へ出す手当てを入れておくと切り分けが1往復で済む |

### 4.3 どちらの構成でも共通

| 事項 | 規則 |
|---|---|
| ブラウザURL | 詳細がモーダルで開くためURLにoidを含まない。URLからは取れない |
| テナントのベースURL | JS側で `window.location.pathname` から組み立てる。詳細画面(MDC)では `/mdc/` の手前まで、単独ページ(§4.4)では先頭2階層(コンテキストパス + テナント名)。**両方で動かすなら `/mdc/` の有無で分岐させる**(片方の前提で書くと、もう片方でAPIが404になる) |
| 他のレコードへ遷移するリンク | 詳細画面のURLは `<ベースURL>/mdc/entityview/detail/index/<Entity定義名>/<oid>/<バージョン>` の形。**oidはクエリではなくパスに置く**。埋め込み先のブラウザURLは詳細を開いてもモーダルのまま変わらないため、そこからURLの形は分からない。実画面で対象を開いて確かめる |
| WebApi呼び出し | `X-Requested-With` ヘッダを付ける。`GET` では `Content-Type` を送らない |
| 自前のモーダル・重ねる入力欄 | **JSで後から `body` やダイアログの中身へ足す形は使えない。** ダイアログがフォーカスを内側へ引き戻すため、`body` へ足すと**枠は出るが入力できず**、ダイアログの中身の要素へ足すと**表示されない**。**テンプレートセクションのVueが描く重ねパネル（`position: fixed`）なら使える**（Vueの管理下にある要素なので後から足すことにならない）。高さの決め方は§4.1.1。入力が1項目でもこの形で作れる（初期値を出せる・エラーを画面に出せる）ので、ブラウザの入力ダイアログは仮の形にとどめる |
| 素のHTMLの見た目 | MDCの共通CSSが `input` 等の枠線・背景を消す。自前のHTMLを出すなら**枠線・背景・文字色・高さを明示する**。消えていても要素は存在するため「描かれていない」と誤診しやすい(投入した文字列にタグが残っているかを先に見る) |

**投入はバックアップから読み直してセクションを追加する。** 更新は全置換なので、liveを起点にすると実行のたびにセクションが増える。投入後は追加分の保存とあわせて、**既存セクションがバックアップと同一であること**と**プロパティ要素の総数が変わっていないこと**を照合する。

AdminConsoleでの場所は `Data Model` > `Entity` > 対象Entityを右クリック > `MDC EntityView` > `View Control Setting` の対象View行 > `DetailView Layout` の編集。同じメニューにある `GEM EntityView` は別系統で、MDC系の画面を持つEntityではそちらに定義が無い。

**GUIで保存してもセクションの内容は保持される。** レイアウトの並べ替えや他セクションの調整はGUIで行える。ただし実装の正本をファイル側に置く方針は変えない。GUIで本文を直接編集すると正本と乖離するため、本文の変更は生成スクリプト経由で行う。

### 4.4 別タブで開く単独ページにする

詳細画面のモーダルは狭いため、広い画面で見せたい画面は**独立したURLの単独ページ**にする。`ActionMapping` でURLを作り、テンプレート定義を返すだけの構成にできる。**MDCの画面（ヘッダ・検索画面・詳細モーダル）は使わない。**

| 定義 | 内容 |
|---|---|
| `ActionMappingDefinition` | `name` がURLのパスになる（`<ベースURL>/<name>`）。`result` に `TemplateResultDefinition`（`commandResultStatus` は `*`）を1つ置き、`templateName` でテンプレートを指す。**Commandは不要** |
| `HtmlTemplateDefinition` | ページ全体のHTML。`contentType` は `text/html; charset=utf-8`（**ヘッダ名は含めない**。含めると文字化けする） |

Vueは**MDCのフロントエンドから `createVueApp` だけを借りる**。`<script>` で `<コンテキストパス>/static/mdc/iplass-mdc.umd.js` を読み込み、`onload` で `Mdc.createVueApp(<コンポーネント>).mount(<セレクタ>)` を呼ぶ。読み込み前は「読み込み中」の要素を出しておき、`onload` で隠す・`onerror` でメッセージに差し替えると失敗が画面に出る。

この経路の制約は3つ。**Vue SFCの書き方はそのまま持ち込めない。**

| 制約 | 書き方 |
|---|---|
| `Vue` 本体が公開されておらず `ref` / `computed` / `onMounted` をimportできない | **options API**（`data` / `computed` / `methods` / `mounted`）で書く |
| SFCとしてコンパイルされないため `<template>` ブロックが使えない | テンプレートは `<script type="text/x-template" id="...">` に置き、`innerHTML` で読んでコンポーネントの `template` に渡す。**自分自身を参照する再帰描画もこの方法で書ける**（描画関数は要らない） |
| MDCの画面部品（`m-i-` で始まるカスタム要素・詳細画面のコンポーネント）は使えない | `app.use` が必要という趣旨のエラーになる。使うなら `Mdc.useMdc(<設定>)` で画面ごと起動することになり、MDCのヘッダ・検索画面・モーダルの枠が付いてくる（枠をCSSで隠す形になり、MDCのクラス名に依存する） |

対象レコードのoidは**クエリで渡す**（`?<名前>=<oid>`）。詳細画面のボタンから `window.open` で別タブに開く（ボタンは下表、oidの取得は §4.2）。

**投入前の機械検査（§4.1の3点）は同じように行う。** タグの開閉・JSブロックのパース・テンプレートが参照する識別子の定義を確かめる。テンプレートを `<script type="text/x-template">` に置く場合は、`ref` 属性のように**JS側の定義を要さない属性を検査対象から外す**（外さないと誤検知になる）。書けない文字列（改行のエスケープ・`${`・`<% %>`）の規則は§4.2の表と同じで、生成スクリプト側で弾く。

**テンプレート定義に `layoutActionName` を設定してはいけない。** 単独ページ化には効果がないうえ、**セクションとして描画する経路まで壊れる**（画面の読み込みに失敗する）。

**画面のボタンは `detailView` のボタン配列で足す。** セクションの中にボタンを描くより、画面の操作として並ぶので分かりやすい。

| 場所 | 配列 | `@class`（`...detail.definition.button` 配下） |
|---|---|---|
| 画面上部 | `topAreaButtons` | `MdcDetailTopAreaButton` |
| 下部の操作バー | `bottomBarButtons` | `MdcDetailBottomBarButton` |

主なフィールドは次のとおり。ほかに `displayView` / `displayCreate` / `displayUpdate`（出す画面の選択）がある。

| フィールド | 内容 |
|---|---|
| `type` | `CUSTOM_BUTTON` |
| `displayLabel` | ボタンの文字 |
| `iconTag` | **Material Design Icons の名前に `mdi-` を付けたもの**（例 `mdi-sitemap-outline`）。名前は一覧サイト（[Material Design Icons - Pictogrammers](https://pictogrammers.com/library/mdi/)）で探す |
| `primary` | `true` で塗りのボタン、`false` で控えめな見た目になる |
| `displayMethod` | `SOLO` か `MENU`（下記） |
| `onclick` | 任意のJavaScript。何もしないボタンにするなら `void 0;` |

**`displayMethod` でボタンをメニューへ入れられる。** ボタンの数が多いときはこれで整理する。

| 値 | 画面上の扱い |
|---|---|
| `SOLO` | 単独のボタンとして並ぶ。**画面上部では `iconTag` が無いと単独では出ず、メニュー側へ回る** |
| `MENU` | メニューの中に入る。数が多いボタン群はこちらにまとめると、画面が横に伸びず一覧もできる |

**「画面幅に入りきらない分だけメニューへ回す」挙動は無い。** 振り分けは `displayMethod` の静的な条件分岐だけで、幅は見ていない。場所ごとの扱いは次のとおりで、**単独にできる数は場所で決まる**。

| 場所 | 扱い |
|---|---|
| 画面上部の浮いたバー | `SOLO`（かつ`iconTag`有り）をラベル＋アイコンのボタンとして**横1列**に並べる。折り返しが無いため、数が多いとボタンが縮んでラベルが潰れる。`MENU` が0件ならメニュー自体が出ない |
| 下部の操作バー | `SOLO` は標準ボタン（削除・コピー・ロック等）と一緒に並び、入りきらなければ**折り返す**。ロック・バージョン等の標準ボタンも同じメニューに入るため、`MENU` を0件にしてもメニューは残る |

**下部の操作バーだけは、条件が揃うと `SOLO` も含めて全部メニューへ畳む。** 条件は「超小画面、または詳細の表示幅が指定されている」かつ「ボタン総数が4を超える」。**通常のモーダル表示では畳まれない**ので、`SOLO` は個別のボタンとして出る。畳む/畳まないの分かれ目は画面側の実装（`MIDetailAppBarContent`）にあり、定義からは読めない。**実画面で確かめる。**

幅で動かしたくなっても、描かれたボタンのDOMを触る形になる（クラス名依存＋再描画で崩れる）ため選ばない。単独で出すボタンを絞るか、数を減らす。**この判断の根拠は画面側の実装にあるので、挙動が疑わしいときは `<コンテキストパス>/static/mdc/iplass-mdc.umd.js` を取得して `displayMethod` の使われ方を読む**（公式ドキュメントには出ていない）。

**実在しない `iconTag` を書いてもエラーにならず、アイコンが出ないだけになる。** 投入前に `<コンテキストパス>/static/mdc/materialdesignicons.min.css` を取得し、`mdi-<名前>::before` があるかで照合する。

**画面上部のバーは使わないという選択ができる。** ボタンの配列を空にすればバー自体が出ない。折り返しが無いため単独で並べられるのは数個までで、画面が狭いと縦積みの大きなボタンになって上部を占める。同じボタンは下部の操作バーにも置けるので、**上部を空にして下部だけで済ませる**のが扱いやすい。

**下部の操作バーの並び順は定義では変えられないが、CSSで見た目の順序を変えられる。** 描画順は「メニュー → 単独ボタン → 標準ボタン」で固定されている。順序を変えたいときは次の形にする。要素を動かさないので再描画で崩れず、当たらなければ今の並びのままになる。

| 手順 | 内容 |
|---|---|
| 1 | ボタン定義の `cssClassName` に独自クラスを入れる（定義が公開しているキーなので、描かれたDOMを触るのとは違う） |
| 2 | ラベルを空にしたスクリプトセクションへ `<style>` だけを置く（画面には何も出ない） |
| 3 | 入れ物のクラス名は分からないので `:has()` で特定する（メニューのボタンと標準ボタンの両方を直接の子に持つ要素）。その上で `order` を振る |

**独自クラスは、その画面のすべてのカスタムボタンへ付ける。** 付いていないボタンだけが標準ボタンと同じ扱いになり、メニューの右へ回る（別の作業で足されたボタンが混ざると起きる）。生成スクリプト側で「残した既存ボタンにも付ける」ようにしておく。

**`elementRuntimeId` は送信した値が保存されず、サーバー側で振り直される**（`<場所>-area-button-<連番>` の形）。**ボタンの重複を避ける判定にidを使わない**（liveを起点に再実行したときに効かず、同じボタンが増える）。ラベルのように保存される値で判定する。

**`onclick` から開いているレコードのoidは直接取れない。** oidを `window` へ入れるスクリプトセクションを併置し（§4.2）、`onclick` からその値を読む。

**`onclick` からテンプレートセクションのVueへは、window イベントと `window` の印の2本立てで伝える。** ボタンで入力用のダイアログを開く構成はこれで作れる（`onclick` は合図だけを出し、入力・通信・遷移はVueが持つ）。**印も併せて見るのが要点**で、セクションのVueが載る前にボタンが押されるとイベントは誰も受け取らないため、Vue側は `onMounted` で印（真なら開く・開いたら消す）も確かめる。イベントだけに頼ると「押しても何も起きないボタン」になる。

**Viewをもう1つ作って目的のセクションだけを出す形は選ばない。** 別のViewを`viewName`で分けて開く経路もあるが（View名はパスではなくクエリで渡す。パスへ足すとバージョンの型変換で失敗する）、詳細画面のモーダルとして開くためヘッダと操作バーが残り、URLもEntityの詳細画面のものになる。**単独ページで足りるならView定義を増やさない。**

### 4.5 MDCの全画面で動くJSを載せる

埋め込みの2つの構成（§4.1・§4.2）はどちらも**そのEntityの詳細画面でしか動かない**。トップ・検索・詳細の
すべてで動くJS（アプリバーへ足した項目に印を出す等）が要るときは、**MDCのレイアウトActionを入れ子にする**。

MDCの画面はすべて共通のレイアウトAction（`action/mdc/layout/defaultLayout`）を `layoutActionName` に
指定していて、そのレイアウトは製品のJSPを返す。**JSPの中身は触れないが、そのレイアウトAction自身の
`result[0].layoutActionName` にこちらのレイアウトActionを指定すると、製品のレイアウトを包める。**

| 事項 | 内容 |
|---|---|
| 作るもの | GroovyTemplateのテンプレート定義1つと、それを返すAction定義1つ |
| 包まれた側の位置 | テンプレートの `<%renderContent()%>`。そのあとに `script` を置けば全画面で動く |
| 触る既存定義 | 共通のレイアウトActionの `result[0].layoutActionName` を**1つ足すだけ**（`templateName` は変えない） |
| 影響範囲 | **MDCの全画面**。壊れると全画面が出なくなるので、結線の直前にliveを退避して戻せるようにする（作法は [iplass-definition-io](../iplass-definition-io/SKILL.md) §9） |
| 影響しない画面 | ログイン画面はレイアウトを使っていない |
| GroovyTemplateに書けない文字 | `${` と `<%`、`script` の閉じタグ。投入前に機械で検査する |

**共通のレイアウトActionは他の作業と共有する。** 足すキー以外に差分が無いことを機械で照合する。

## 5. SFのロジックをiPLAssへ写す規則

| SF側 | iPLAssでの扱い |
|---|---|
| 数式(`formulaTreatBlanksAs = BlankAsZero`) | nullを0として扱う処理を明示する。省くとSFと結果がずれる |
| 数式が数式を参照 | 素の項目まで展開して計算する |
| ロールアップ集計 | iPLAssに相当機能が無い。値を保持する形で移行されるため自動再計算されない。再計算はイベントリスナかクエリ集計で別途手当てする |
| レコードIDによる並び順 | 作成日時で代用する。データ移行時にSF側の作成日時を引き継ぐ |
| 祖先のキーを連結した多階層ソートキー | 再現しない。木構造を再帰的に組むなら、兄弟単位で並べれば同じ木になる |
| 並び順の空値の位置 | クエリの `ORDER BY` に任せず、取得後にコード側で並べる。SFは空値を末尾に置く |
| 階層の深さによる色分け | 深さの剰余で決まる。データ側に項目は不要 |
| 判定の順序 | 写すのが既定。**到達する終状態とメッセージが全ケースで同じなら変えてよい**（例: できない理由を先に出し、無駄な確認を求めない）。変えたら理由を記録する |
| 分岐で作るレコードの種類が非対称 | 揃えずに写す。移植元の現行動作を保つ。業務上おかしいと見えても、意味を変える判断は別の課題として起こす |
| 同じ選択肢を別のEntityへ渡す | 両側の値集合が一致しているかを定義で確かめる。移行時に表示ラベルを値にした側があると、一致しない値が**黙って落ちる**(例外もログも出ない)。対応表は [property-mapping.md](../converting-salesforce-to-iplass-entity/references/property-mapping.md) §7 が定義位置 |
| カスタムラベルで持つ設定値(閾値・初期値等) | **ラベルの定義は移行元のメタデータに含まれない。** 値は移植先のCommandへ写すことになるので、**採取した値を申し送りへ記録する**(ツールの出力側は消えると復元できない)。値そのものはスキルに書かない |
| 外部ライブラリでのDOMの画像化 | 静的リソースを増やさずに済む。SVGの `foreignObject` にHTMLを入れて画像としてcanvasへ描くのが同じ原理。**`foreignObject` の中身はXMLとして解釈される**ため、DOMは `XMLSerializer` で直列化する（HTMLのままでは実体参照や閉じていない要素でパースに失敗し、画像化が理由の分からない失敗になる）。`DOMParser` で先にXMLとして読めるか確かめると原因が画面に出せる |

移植元の数式・集計の定義は `force-app/` の項目メタデータを一次情報として引く。iPLAss側の現状(型・Expression化の有無)は live定義を取得して確認する。

## 6. 開発を回すときの注意

Commandを直しながら画面を作るときは、**定義を更新しても実行に反映されない**ことがある。反映の作法と回避策は [iplass-definition-io](../iplass-definition-io/SKILL.md) §4 が定義位置。画面側(スクリプトセクションのHTML・CSS・JS)は更新がそのまま反映されるため、**サーバー側の形が固まってから画面を作る**と反復が速い。

**curlで自作のWebApiを叩いて確かめるときは、`POST` の本文を自前でパーセント符号化する。** 素で送ると日本語が化けて保存され、Select型では選択肢に一致せず**原因の見えない500**になる(符号化しない理由と方式は [iplass-entity-crud-api](../iplass-entity-crud-api/SKILL.md) §6 が定義位置)。**画面から `fetch` で送る分はブラウザが符号化する**ため、この問題は確認用の呼び出しだけで起きる。値が化けていないかは、投入後に取得して読み戻して見る。

## 7. SFの見た目を写す規則

SF側のCSSは階層ごとにファイルが分かれ、**同じクラス名が階層ごとに別の指定を持つ**。移植先で共通クラスへまとめると、写し漏れが並び方の違いとして出る。

| SF側 | iPLAssでの扱い |
|---|---|
| 同名クラスが階層ごとに別ファイルで定義されている | 共通クラス＋差分クラスにまとめるなら、**差分側で `display` を明示する**。基底の `display: inline-block` を引き継いだ要素は横に並び、文字の基準線で揃えられて枠の上端が段違いになる |
| 値が無い項目を条件付きで消している(`lwc:if` / `v-if`) | 枠の中の段を揃えるなら消さずに空文字の行を出し、**行の高さをCSSで固定する**。継承の `line-height` に任せると空の行だけ低くなって段がずれる |
| 枠を段ごとに横並べしている(`display: flex`) | 複数段の枠の縦横を揃えるなら、段ごとに並べず**1つの格子(`display: grid`)へ入れる**。列の幅は列内で広い枠、行の高さは行内で高い枠に揃う |

格子のマス目いっぱいに枠を広げるときの規則。

| 事項 | 規則 |
|---|---|
| 枠の大きさ | `width: 100%` / `height: 100%` を付ける。**表(`table`)は内容の大きさで決まるため、付けないとマス目より狭いまま**になる |
| 枠の間隔 | `margin` ではなく `gap` で取る(`margin` は広げた枠をマス目からはみ出させる) |
| 列の幅 | `max-content` にすると列内で一番広い枠に揃う。枠側が `width` を固定で持つと列の幅より優先されるため、**下限は `min-width` で書く** |

## 8. 画面の見た目を確かめる

業務画面はログインを要するため、投入した定義がどう見えるかを画面から直に測れない。**CSSの正本を読むだけの静的HTMLをローカルに立てて測る。**

| 手順 | 内容 |
|---|---|
| 1 | 画面が描くのと同じDOMを写した静的HTMLを作る。CSSは `work/` の正本を `<link>` で読む(複製しない) |
| 2 | ローカルのHTTPで配る。ブラウザを操作する経路は **`file:` を開けない**ため、`127.0.0.1` の簡易サーバ経由にする |
| 3 | 枠と行の位置・大きさを測り、**揃うべきものが一致しているか**で判定する |

MDC側の共通CSSは再現されないので、**行の高さの絶対値は実画面と違う**。判定は枠どうし・段どうしの一致で行い、実画面での確認は画面を見られる人に依頼する。静的HTMLはGit管理外の作業場所に置き、測り終わったらサーバのプロセスを止める。

### 8.1 SF側の見た目の値をもらう

移植先の見た目をSFへ寄せるとき、**SFのHTMLをもらっても値は取れない**。ブラウザから採れるHTMLはフレームワークの起動用スクリプトと共通CSSが大半で、レコード画面の枠や項目行の値はその中に無い。CSS変数（デザイントークン）の既定値までしか読めない。

**必要なのは開発者ツールの Computed（計算済み）パネルの値**である。要素を選んで、その要素の確定した値をもらう。頼むときは対象を名指しする（枠・項目1行・タブ1つ・見出し1行など）。得られる値は次の形になる。

| 見るもの | 得られる値 |
|---|---|
| 文字 | `font-family` はシステムフォント（`-apple-system, BlinkMacSystemFont, "Segoe UI", …`。`Salesforce Sans` ではない）・`font-size: 13px`・`line-height: normal`・`color: rgb(24,24,24)` |
| 枠（カード） | `padding: 8px 12px`・`border: 1px solid rgb(201,201,201)`・`border-radius: 4px`・`box-shadow: rgba(0,0,0,.1) 0 2px 2px` |
| 項目 | ラベルは `12px` / `#444444`・**値の上に置く縦積み**・行ごとに細い区切り線 |
| タブ | 器は `padding: 0 12px` / 高さ `40px`、文字は `16px`、下線は**文字幅ぶんだけ**（器の幅ではない）・選択中は `font-weight: 700` |
| 見出し | `background: rgb(243,243,243)`・高さ `32px`・`padding: 0 8px`・`border-radius: 4px`・枠線なし |

**SFの画面はShadow DOMの中にある。** 要素をまとめて拾うスクリプトを渡して採ってもらうときは、`document` の検索だけでは
**1件も当たらない**（採れたつもりで空の結果が返る）。shadow rootを再帰的に辿る必要がある。当たったかどうかが結果から分かるよう、
部位ごとに見つかったかの真偽を一緒に返す形にしておく。クラス名ではなく**画面に見えている文字**（見出し・ボタンの名前）で
要素を特定すると、相手側のクラス名が変わっても当たる。

**採った数値は、コードから読めるGit管理の正本（モジュール）に置く。** 作業場所（Git管理外）に置くと消えて復元できない。
そのうえで**CSSがその値どおりかを機械検査する**と、値の出所が1つに保たれ、後からCSSだけを直して設計とずれる事故が防げる。

Computedの値で決めた箇所と、こちらで決め打ちした箇所は、**コード側のコメントで区別して書く**（次に詰めるとき、どこを聞けばよいかが分かる）。SLDSのトークン名から既定値を引くのは、値をもらえないときの代用にとどめる。

**見た目をSFへ寄せるかどうかは案件ごとの判断で、既定ではない。** 移植先の画面をSFの色・配置に合わせる作業は、どこまでカスタマイズできるかを確かめる目的や、利用者に同じ画面として見せる目的があるときに行う。目的が無ければ、移植先の標準の見た目のままにする（合わせた分だけ、SF側の変更に追随する手間が増える）。

## 9. タブで構成された画面をMDCで再現する

**MDCの詳細Viewにタブのセクション種別は無い**（セクションは標準・スクリプト・テンプレート・バージョン・操作ログ・大量データ参照・ワークフロー履歴の7種。種別ごとの役割は [converting-salesforce-layout-to-iplass-view](../converting-salesforce-layout-to-iplass-view/SKILL.md) §2）。SFのページレイアウトがタブで構成されているとき、再現の形は2つあり、**既存のセクション（項目・関連リスト）をそのまま中身に使いたいか**で決まる。

| 形 | 作り | 向くとき | 効かないとき |
|---|---|---|---|
| セクションを出し入れする | タブバーのスクリプトセクションを1つ足し、自セクション内の`<style>`の中身を書き換えて、選択中のタブに属さないセクションを`display:none`にする | 項目・関連リストの表示（ソート・ページング・詳細ダイアログ）をMDCのまま使いたい | セクションの並びを特定できないと切り替えが効かない（画面は縦積みのまま残る） |
| 1つのテンプレートセクションに全部描く | 詳細Viewをテンプレートセクション（§4.1）＋oidを渡すスクリプトセクション（§4.2）だけにし、Vue SFCでタブ・項目・表を描く | タブ構成と見た目を自由に作りたい／MDCの内部構造に依存したくない | 項目の描画とデータ取得を自前で持つ（表示専用でもWebApiが要る） |

タブの中身が**既に単独ページとして作ってある画面**なら、3つ目の形として**枠（iframe）で読み込む**選択がある（§9.3）。単独ページ用の実装はSFCへ持ち込めない（§4.4）ため、作り直さずに使うにはこの形になる。

### 9.1 セクションを出し入れする形

- **描かれたDOMは動かさない。** `display` の指定だけで切り替える（要素を動かすと再描画で崩れる。§4.4の下部バーをCSSで並べ替える判断と同じ理由）
- セクションは**自分のDOMから親を辿り、子要素の数が定義のセクション数と一致する要素**を「セクションの並び」とみなし、並び順の番号で指す（クラス名に依存しない）
- 特定できなかったときは**何も隠さない**。画面は縦積みのまま残るので壊れず、注意書きだけ出せる
- **画面に出る順序は定義の順序**である。タブの割り当てだけでは並べ替えられないので、ある枠を一番下に見せたければ**定義側でセクションを末尾へ動かす**
- タブごとに「そのタブと祖先に割り当てたセクション」を出すと、SFの「親タブの中身＋選択中の子タブの中身」と同じ見え方になる
- 上部タブと同じ遷移を担うカスタムボタンが下部バーにあると役割が二重になる。**タブを足すときは重複するボタンを外す**（`type` が `CUSTOM_BUTTON` の要素だけを落とす。標準ボタンはこの配列に無いので影響しない）

### 9.2 テンプレートセクションに全部描く形

- **項目の表示名はEntity定義の `displayName` が出所である。** 詳細Viewの要素も参照セクションの列も表示名を持たない（要素の `editor` が持つのは `type` / `displayType` / `maxLength` 等）ため、View定義だけから画面を作ると**ラベルがAPI名のまま出る**。関連リストの列は**子Entity**の定義から引く（親の被参照プロパティ名から子Entity名を解決する）
- 項目の並び・枠の区切り・関連リストの列は**View定義から生成する**（手で並べ直さない）
- 中身がまだ無いタブは、ダミー（インラインSVG等。外部画像を持たない）と「未移行」の空枠を**見分けが付く形**で置く。実データのタブと混同させない
- データは1本のWebApi（GET）でまとめて返す。応答は**値が `null` のキーが落ちる**ので、画面側は「キーが無い＝null」として読む（§3）

### 9.3 既に作った単独ページを枠（iframe）で読み込む

タブの中身が単独ページ（§4.4）として既にあるなら、枠で読み込めば実装を作り直さずに済む。**同じテナントなので同一オリジン**で、認証も同じセッションが効く。枠内表示を妨げるヘッダー（`X-Frame-Options` / CSP）が返っていないことは、`GET` の応答ヘッダーで確かめられる（ログイン前でも確認できる）。

| 事項 | 決め |
|---|---|
| oid | 枠のURLのクエリで渡す。値は併置のスクリプトセクションが `window` へ入れたものを読む（§4.2） |
| 読み込むタイミング | **そのタブを表示した時点**で `src` を入れる（隠れている間に読み込ませない）。テンプレートセクション方式なら `v-if` で枠ごと作り直すので自然にこうなる |
| 幅 | スクリプトセクションの入れ物は**内容幅に縮む**ため `width: 100%` では広がらない。セクションの並び（タブバーが目印を付けた要素）の実寸から決めてpxで指定する |
| 高さ | 中身が必要とする高さ（`scrollHeight`）を枠に与え、枠の内側にスクロールを出さない。**中身の `html` / `body` が `height: 100%` だと枠の高さをそのまま返す**ので、読み込み時に `height: auto` を差し込んでから測る |
| 大きさの追随 | ウィンドウのリサイズに加えて、**詳細画面のダイアログの拡大・縮小は `resize` を出さない**ので、表示中は定期的に測り直す |
| 別タブへの逃げ道 | 枠の見出しに「別タブで開く」リンクを置く。狭いダイアログでは広い画面が要ることがある |

**単独ページが `Mdc.useMdc` でMDCのヘッダー・サイドメニューを出している場合、枠に入れるとそれが二重になる。** URLのパラメータ（例 `embed=t`）で**レイアウトの起動を飛ばす分岐**をテンプレートへ入れる。マウント先をレイアウトのスロットで待っている実装なら、その待ち条件も分岐させる。**単独ページとして開くときの挙動は変えない**（パラメータが無ければ従来どおり）。

同一オリジンなので、枠の中のDOMへ**親から触れる**（高さの測定・CSSの差し込み）。中身を作り直さずに見た目を整えられるが、触る先は最小限にとどめる（相手の実装に依存が増える）。

### 9.4 管理コンソールとの共存

**表示画面をテンプレートセクションで作ると、編集画面が白紙になる。** 表示専用のセクション（`displayView` だけを立てたもの）しか無いためで、**編集・新規だけに出す標準セクション**を別に置く。

この標準セクションは**項目の枠（並び・区切り・ラベル）の正本にできる**。同じセクションを表示画面のVueにも生成時に渡せば、**管理コンソールで並べ替え・追加・削除した内容が表示画面と編集画面の両方に入る**。二重管理を避けるうえ、GUIでの調整が効くようになる。

| 事項 | 規則 |
|---|---|
| 生成の入力 | そのView自身のliveを渡し、標準セクションはそのまま持ち越す。初回だけ他のViewから写す（写し直す操作は明示的な引数にする） |
| Vue側の突き合わせ | セクション名で突き合わせない（GUIで名前を変えられる）。「このタブはその枠を全部出す」と決める |
| 関連リストの列 | 参照セクションを持たないViewでは採れないので、**出所を別のViewにする**（引数で分ける） |
| 反映のタイミング | GUIで直した内容は**再生成・再投入するまで表示画面に入らない**（編集画面だけが先に変わる）。この非対称をユーザーへ伝える |

**セクションを出し入れする形（§9.1）では、GUIでの操作に制限が付く。** タブの割り当てをセクションの**並び順の番号**で持つため、次のようになる。

| GUIでの操作 | 影響 |
|---|---|
| セクション内の項目の並べ替え・追加・削除 | 影響なし |
| セクション自体の並べ替え・追加・削除 | **割り当てがずれる**。生成スクリプトを再実行して投入し直す |
| どのセクションをどのタブに出すか | GUIでは変えられない（割り当て表を直す） |

**役目を失ったセクションは落とす。** 中身がCSSだけのセクション（カスタムボタンの並べ替え用など）は、そのボタンを外した後は**中身が空のまま開閉できる枠**として画面に残る。持ち越しの対象から外す（判別は本文に埋めた目印で行う）。

どの形も、投入前の機械検査（§4.1の3点・書けない文字列）と、実画面での確認（§8）は同じように行う。

### 9.5 標準の編集画面の見た目を寄せる

表示画面を作り込むと、**編集・新規画面だけが移植先の標準の見た目のまま残り、画面を移った瞬間に別の製品に見える**。
編集画面はMDCが描くため作り替えられないが、**編集・新規だけに出すスクリプトセクション（`displayCreate` / `displayUpdate` のみ）に
CSSを1つ置けば見た目は寄せられる**。表示画面には出ないので、表示側の作り込みと干渉しない。保存・入力チェック・参照選択・添付は
MDCのものがそのまま残る。**動作が変わったなら、CSSがMDCの要素を隠した兆候**として扱う（`display: none` を指定した箇所を疑う）。

編集フォームの骨格は次のとおり。**列は既に2カラム**なので、カラム数は寄せる必要がない。

```
セクションの外枠 → 開閉パネル → 見出し（ボタン） → 中身
  → 行 → 列（1/2幅） → 項目の枠 → ラベル ＋ 値の欄（入力）＋ 操作の欄
                                          └ 注記・エラーの欄
```

| 部位 | 移植先の作り | 寄せ方 |
|---|---|---|
| ラベルの位置 | **入力欄の上**に出る | 左に出すなら項目の枠を `display: grid` の2列にする。要素は動かさない |
| 必須 | **赤いチップ**（文字つき） | 印を変えるならチップの文字を `font-size: 0` で消して疑似要素で置き換え、`order` でラベル内の位置を変える |
| 入力欄 | 下線だけ（重ね背景と下線の要素を持つ） | 全周の枠にするなら枠を付け、重ね背景と下線の要素を消す |
| 注記とエラー | **同じ要素**に出る | エラーだけ色を変えるなら、エラー時に付くクラスを前置する |
| 複数行の入力 | 1行の入力と同じ並び | 元画面でラベルが上・幅いっぱいなら、その型だけgridを1列へ戻す |

**移植先の画面フレームワークのユーティリティクラス（余白・背景・角丸）は `!important` を持つ。** 打ち消す箇所だけ `!important` を使い、
それ以外では使わない（どこが打ち消しなのかが読めなくなる）。

CSSの正本はファイル1つにして、生成スクリプトが読んで `<style>` として埋め込む。**セクションの本文へ目印を埋める**と、
持ち越しの判別（役目を失ったセクションを落とす）に使える。

## 10. 画面フロー(Flow)の移植

SFの独自画面には、LWCで作られたものと**画面フロー(screen flow)**で作られたものがある。判定(§1)・段階分け(§2)・移植先の構成(§3・§4)は共通で、違うのは**移植元の読み方**と、フローが持つ**複数の画面**と**レコード作成の連鎖**の写し方である。

### 10.1 フローの読み方

フローの定義は1ファイルのXMLで要素数が多い。全文を読む前に**構造だけを取り出す**。要素種別の数を数える → 要素種別と名前の対応を出す → 必要な要素の本文だけ読む、の順で進める。座標とビルダーの付帯情報は読み飛ばす。

起点は`start`要素で、`connector`の`targetReference`を辿ると経路が確定する。**分岐は既定の経路(`defaultConnector`)とルール(`rules`)の2系統を持つ**ので、両方を辿らないと片方を見落とす。

**分岐のルールは複数の条件を持つ。`conditionLogic`を必ず読む。** `and`か`or`かで意味が反転する。
1つ目の条件だけを読んで判断すると、**逆の結論を出したうえでそれを移行先の仕様として記録してしまう**。

| 見落としの形 | 起きること |
|---|---|
| `or`のルールの1つ目だけ読む | 「移行元はこの判定をしていない」と誤認し、移行先で足した処理を「移行元と違う」と記録する |
| `and`のルールの1つ目だけ読む | 移行先で条件を絞りすぎ、通るはずのものが通らなくなる |

条件が2つ以上あるルールは、**条件の全部と`conditionLogic`を書き出してから**移行先の判定を書く。

**条件には省略形がある。** 比較の右辺(`rightValue`)を持たない条件は、値の比較ではなく
**「空かどうか」を見ている**（移行元がコレクションや参照の空判定をこの形で書き出す）。
右辺が無いのを「読み取れなかった」と扱わず、空判定として写す。判断に迷ったら、
**同じ項目を使っている他の分岐**が同じ形か比較すると意図が読める。

### 10.2 フロー要素と移植先の対応

| フローの要素 | 移植先 |
|---|---|
| 画面(`screens`) | Vue SFCの段。1つの画面が1つの段になる |
| 画面の入力欄 | 段の入力欄。必須・既定値・入力検証をそのまま写す |
| 画面の表示テキスト | 段に出す文言。HTMLタグを落として本文だけ写す |
| レコード検索型の部品(lookup) | 前方一致検索のAPIと候補一覧(§3) |
| 分岐(`decisions`) | Commandの中の条件分岐。**順序も写す** |
| 代入(`assignments`) | Commandの中の値の組み立て |
| レコード取得・作成・更新 | Commandの中の検索・作成・更新 |
| ループ(`loops`) | Commandの中の繰り返し。取得順は§5の規則で決める |
| 数式(`formulas`) | 既定値や表示の計算。素の項目まで展開する(§5) |
| Apexの呼び出し(`actionCalls`・`actionType`が`apex`) | 呼び出し先のクラスを読んで同じ処理をGroovyで書く |
| **移行元の標準アクションの呼び出し**(`actionCalls`・メール送信や通知等) | 移行先の**対応する機能**を探す(§10.6)。相当が無ければ保留に起こす。呼び出し先が移行元のプラットフォーム機能なのでコードを読んで写すことはできない |
| カスタムラベル参照 | 実体がリポジトリに無いことがある。値が分からなければ**仮の値を置いて保留に起こす** |

画面の入力欄は種別ごとに部品が決まる。見た目の作り方は§4.1.2が定義位置。

| フローの入力欄の種別 | Vue側の部品 |
|---|---|
| 単一行の入力(`InputField`) | 型に応じた `input`(文字列・数値・日付) |
| 複数行の入力(`LargeTextArea`) | `textarea` |
| 選択肢(`DropdownBox` / `RadioButtons`) | `select` / `input[type=radio]`。**値が空の選択肢にラベルを付ける**(§4.1.2) |
| レコード検索型の部品(`ComponentInstance` の lookup) | 検索欄＋候補一覧＋選択済みの表示(下記) |
| 表示のみ(`DisplayText`) | 段に置く文言 |
| 段組み(`RegionContainer` / `Region`) | 段の中のレイアウト。段を分ける理由にはしない |

レコード検索型の部品は、**候補を選んだあとの状態も持たせる**。検索して1件選ぶだけでは、選び直せない画面になる。

| 状態 | 画面の見え方 |
|---|---|
| 未選択 | 検索欄と検索ボタン。空の検索語では候補を出さない(§3) |
| 候補あり | 候補の一覧。同姓同名を選び分けられるよう、名前だけでなく識別できる項目も並べる |
| 選択済み | 選んだレコードの表示と「選び直す」。**oidを保持し、送信時にoidを渡す** |
| 既定値がある場合 | 最初から選択済みの状態にする(フローの `recordId` 相当の入力値を写す) |

**画面の入力検証と、分岐の先に置かれたエラー画面は別物**である。同じ内容の検証でも**文言が違うことがある**。どちらもサーバ側に置き、文言は分岐ごとに写す。**画面側にも同じ検証を置く**と、送信前にその場で出せる。

入力検証が正規表現(`REGEX`)の場合、**SFの `REGEX` は文字列全体に一致する**ので、先頭と末尾の指定が無いパターンには補って移す。パターンの変換規則は [validation-rule-mapping.md](../converting-salesforce-to-iplass-entity/references/validation-rule-mapping.md) が定義位置(Entity側のValidatorと同じ規則を使う)。**Entity側のValidatorで足りるなら画面には置かない**——保存時に弾かれるので二重に持たない。画面フローの検証が**Entityの項目に対応しない値**(段をまたぐ入力の組み合わせ等)を見ている場合だけ、画面とサーバ側の処理に持つ。

### 10.3 段の作り方

**まず画面を「入力を受けるもの」と「結果だけを見せるもの」に分ける。** フローの画面はどちらも
`screens`要素だが、移行先での扱いが違う。

| 画面の中身 | 移行先での扱い |
|---|---|
| 入力欄(`InputField`等)を持つ | **段にする** |
| 表示テキスト(`DisplayText`)だけ | **段にしない。** 結果・エラーの表示なので、段の中のメッセージにする |

**入力欄を持つ画面の数で段の構成が決まる。**

| 入力欄を持つ画面 | 段の構成 |
|---|---|
| **0（押すと実行されるフロー）** | 「確認」と「完了」の2段。確認の段には、実行すると何が起きるかを判断できる材料を出す |
| 1 | 「入力」と「完了」の2段 |
| 2以上 | その画面数と同じ数の段＋完了。段を1つに畳まない（入力の途中で分岐が決まる形をそのまま写せる） |

| 事項 | 決め |
|---|---|
| 段の遷移 | 前の段へ戻せるようにする。戻っても入力値を保つ |
| 分岐で入力欄が変わる場合 | 段の中で欄を切り替える。段を増やさない |
| 起動できない条件 | 最初の段の前に判定し、理由だけを出して入力欄を出さない |
| 完了 | 完了専用の段を持つ。文言はフローの完了画面から写す |

フローが完了画面でリンクを出している場合、mdcの詳細はモーダルで開くため同じ体験にならない。**遷移で代える**(§4.3のURLの形)。

### 10.4 レコードの全項目コピー

**まず自分のケースがどちらかを判定する。** フローが**項目を列挙して代入している**なら、この節の除外規則は関係ない(列挙に無い項目は写らない)。フローが**レコードを丸ごと複製している**場合だけ、以下が要る。

丸ごと複製する場合、項目を定数表に列挙しない。**Entity定義のプロパティを走査し、除外規則で外して写す。**

| 除外 | 理由 |
|---|---|
| 採番(AutoNumber) | 新レコードで採番される。設定すると採番を壊す |
| 数式(Expression) | 読み取り専用の計算値 |
| システム項目(`inherited`が真) | 作成日時・更新日時等。SFのDescriptionに対応するプロパティだけは写す例外にする |
| 添付(Binary) | 複製か参照かを決める必要がある。決まるまでは写さない |
| 被参照の参照(`mappedBy`を持つ) | 子側が持つ関係で、値を代入する対象ではない |
| 自己参照 | 作成時には載せられない。作成後の更新で入れる |
| **一意制約(`indexType`が`UNIQUE`系)を持つプロパティ** | 値が入った元レコードで重複エラーになる |
| **移行元のレコードIDを保持する定型プロパティ** | 一意制約とは別の理由でも写せない(下記) |

移行元のレコードIDを保持するプロパティ(`SalesforceId`)は、一意制約があるから除外するのではない。**新しいレコードは元レコードとは別のレコードなので、元の移行元IDを名乗ってはいけない**(移行元から移行先への対応付けが1対多に壊れる)。移行元にこの項目は存在せずフローにも対応する処理が無いため、**フローを写すだけでは漏れる**。定型プロパティの一覧は [property-mapping.md](../converting-salesforce-to-iplass-entity/references/property-mapping.md) §16 が定義位置。

**除外は、全項目コピーを使っている箇所すべてに当てる。** 親レコードだけ直して子レコードのコピーを見落とす形になりやすい。走査する関数の呼び出し箇所を列挙し、除外リストを1つずつ突き合わせる。**移行先の環境でその項目が空のうちは、漏れていても保存が通る**ので、症状が出ないことを根拠にしない。

同じフローの中に、丸ごと複製する箇所と項目を列挙する箇所が混在することがある。**箇所ごとに判定する。**

### 10.5 確認の作り方

**移行先の環境のデータが空だと、通ったように見えて何も確かめられていない状態になる。**

| 確かめたいこと | 元レコードに必要な状態 |
|---|---|
| 項目を空にする処理 | その項目に値が入っている |
| 分岐で扱いが違う項目(片方は保持・片方は空) | その項目に値が入っている。空だと両分岐の結果が同じで区別できない |
| 一意制約を持つ項目の除外 | その項目に一意な値が入っている |
| 値を引き継ぐ処理 | 引き継ぐ元の項目に値が入っている |
| 子レコードが無い場合の経路 | 子レコードを持たない元レコード |
| 参照型の項目を空にする処理 | その参照が実在するレコードを指している |

条件を満たすレコードが環境に無ければ作る。**他機能のフィクスチャらしい名前のレコードは対象にしない**(状態を戻せない変更を加えると他の作業の前提を壊す)。作ったレコードと状態を変えた既存レコードは記録に残す(置き場は [coordinating-migration-work](../coordinating-migration-work/SKILL.md) が定義位置)。

**選択肢に定義外の値を持たせる確認は、レコードを作る形ではできない**(保存時に検証される)。共有の選択値定義を書き換えるのも他の作業に影響する。使い捨てのCommandで判定の関数だけを合成した入力で動かし、確認後にその定義を削除する。

**実行しているユーザー自身に依存する判定**(自分を対象から外す等)は、そのユーザーのレコードを
一時的に変えないと通らない。認証系のデータなので条件を絞る。

| 条件 | 理由 |
|---|---|
| 変更前の値を記録してから変える | 戻す先が分からなくなる |
| 外部へ出ない値を使う | 通知の宛先になる項目は、設定した時点で送信の対象になり得る |
| 設定と復元を**続けて実行し、間に他の確認を挟まない** | 挟むと戻し忘れる。戻し忘れると以降その判定が常に効いたままになる |
| 戻せなければ止めて報告する | 黙って進めると気づかれない |

**認証系のEntityを読む処理は、管理者で通っても一般の利用者で通るとは限らない。** 権限が足りずに
参照が拒否されると、その分を**黙って飛ばす**実装になっていることが多く、**設定漏れと権限不足が
同じメッセージになって切り分けられない**。管理者だけで確かめて終わらせず、一般の利用者で1回通す
（画面の目視確認をその利用者で行えば同時に済む）。それができないなら保留に起こす。

**実データが揃わないと通らない判定は、緩和して先へ進める。** 宛先の解決のように移行先の実データ
（役割の割り当て・利用者の紐付け）に依存する判定は、データが空だと**対象が0件になって操作そのものが
できない**。判定を落とすのではなく、通る側へ緩めて残す。

| 事項 | 規則 |
|---|---|
| 印を付ける | 緩めた行にコードから見て分かる印を付ける（印が無いと本来の仕様と区別できない） |
| 戻す場所を全部挙げる | 同じ判定が起動条件側にもある（§10.6「同じ判定を複数のCommandに持つとき」）。**実行側だけ戻すと画面が「できない」と言ったまま動かない** |
| まとめて戻す単位を書く | 複数の緩和が同じ集合を作っているなら、片方だけ戻すと集合が壊れる |
| 解除の条件を書く | 「何が揃えば外せるか」を1行で書く。緩和ごとに条件が違うなら分けて書く |
| 記録に残す | 置き場は [coordinating-migration-work](../coordinating-migration-work/SKILL.md) が定義位置 |

**緩めた側に有効判定を足さない。** 値の食い違いで対象が再び0件へ戻り、緩和した意味が消える。

トランザクションの巻き戻しも同じ形で確かめられる。使い捨てのCommandでレコードを作ってから巻き戻しを指示し、そのレコードが実在しないことを引いて見る。

### 10.6 フローが通知を送っている場合

移行元のフローは、レコードを作る・更新するだけでなく**通知を送る**ことがある。通知は移行元の
プラットフォーム機能（標準アクション）で行われるため、**コードを読んで写すことができない。**
移行先に対応する機能があるかを先に調べ、無ければ保留に起こす。

| 移行元の通知 | 移行先 |
|---|---|
| メール送信 | メールのテンプレート定義がある。種別と定義パスは `iplass-definition-io` §7 の探し方に従う |
| アプリ内通知・ToDoの作成 | 相当が無いことがある。**受け皿の有無を確かめてから範囲を決める**（無いまま設計を進めると通知が届かない機能になる） |

**受け皿が無い場合、自分で作るなら通知そのものと「気づく手段」の2つが要る。** 通知の実体はEntityで
持てるが、**利用者が気づく場所（帯・ヘッダ）に出す手段は限られる**。アプリバーへ足せるカスタム項目は
**押したときにしか動かない**ため、押す前に未読の有無を出すには全画面で動くJSが別に要る（§4.5）。
受け皿を作る作業は移した機能そのものより大きくなるので、**範囲を分けて先に受け皿を通す。**

**受け皿の有無で移行の範囲が変わる。** 通知がフローの主目的である場合、通知を落とすと
「状態を変えるだけ」の移行になる。着手前に本人へ範囲を確認する。

#### 送るタイミング

**メールはトランザクションのコミット後に送る。** メールは送ってしまうと取り消せないので、
トランザクションの中で送ると、あとで巻き戻ったときに**業務側は成立していないのに通知が届いた**
状態になる。

呼び出しは3段になる。**この骨格を前提に組み、クラス名とメソッドの正確な形は書く前に一次情報を引く**
（メールの送信管理を取る → テンプレート名とバインドする値からメールを組む → 宛先を1件ずつ足す →
送る）。コミット後に走らせる仕組みも同じく一次情報を引く（トランザクションのリスナに登録する形）。
定義位置は `iplass-dev` のスキル（Commandの作法・トランザクション）。

**呼び出し形が分からないまま本体を書き始めない。** §3のとおり記憶で書くと原因の見えない500になる。
先に**使い捨てのCommandでリフレクションからメソッド名と引数の数を並べる**と、一次情報の記述と
実機の食い違いも同時に分かる。

引き換えに次の制約が付く。**設計に書いて画面側の期待を合わせる。**

| 制約 | 扱い |
|---|---|
| 画面は送信の成否を知れない | 応答はCommandが返した時点で確定し、送信はそのあとに走る。画面には業務側が成立したことだけを出す |
| 応答に件数を返すなら意味を限る | 返せるのは**宛先の件数**であって送信できた件数ではない。キー名で区別する |
| 送信の失敗に気づく手段が要る | 例外を握って捨てない。**ログへ出す**（対象のレコード・テンプレート名・宛先の件数・例外） |

#### 送る仕掛けをまだ載せないとき

送信そのものを移行の範囲に入れない（または環境が送信を止めている）ことがある。その場合、
**送信を呼ばずに、送るはずだった内容を1通1レコードとして残す。** 落とすと移行の途中経過を
確かめられなくなる。

| 事項 | 規則 |
|---|---|
| 内容の作り方 | **テンプレートを展開する機能をそのまま使い、送る呼び出しだけを呼ばない**（組んだメールから件名・本文・差出人を取り出す）。展開を自分で書き直すと、テンプレート定義を直しても残る内容が追随しない |
| 状態 | 常に「未送信」。あとで送る仕掛けを載せたときに、残した分を送る対象として拾える |
| 書く位置 | **業務側の更新と同じトランザクション**。レコードなので取り消せる。書けなければ業務の操作そのものが取り消される |
| 送る仕掛けを載せるとき | **送信だけをコミット後へ回す**（上の「送るタイミング」）。記録の位置は変えない |
| 宛先が不完全なとき | アドレスが無い宛先も**誰宛か分かる形で残す**（利用者の識別子を添える）。空欄だと記録が読めない。実際の送信に使う値の一覧は別に保つ |
| 受け皿のEntityの画面 | 他のEntityと同じ形（詳細View・検索View）を用意する。**途中経過を残す先なので、画面から中身を確かめられる必要がある** |

#### 文面とリンク

**件名と本文はテンプレート定義に置き、Commandからは値だけを渡す。** 文面の変更に定義の入れ替えが
要らなくなる。移行元も文面をテンプレートとして持っていることが多く、対応が追いやすい。

**本文のリンクは絶対URLにする。** 画面では表示中のURLからベースURLを組めるが、**メールはサーバ側で
本文を作るのでこの手が使えない。** テナントの定義が持つのはパスだけで、スキームとホストを持たない
ことがある。

**環境ごとに異なる絶対URLの接頭辞は、テンプレート定義に置く。** 移行元も同じものを設定値として
外部化していることが多い。Commandはレコードごとに変わるパスだけを渡す。**環境を移すときに
テンプレート定義の書き換えが要る**ので保留に起こす。

#### 確かめられること・確かめられないこと

**テナントの設定で送信そのものを止めていることがある。** その場合に確かめられるのは次まで。

| 確かめられる | やり方 |
|---|---|
| 宛先が正しく解決されるか | 応答の宛先の件数と、判定の結果を突き合わせる |
| テンプレートが投入され、変数を展開できる形か | 定義を取り直して件名・本文を照合する |
| 送信の呼び出しが例外にならないか | **使い捨てのCommandで同期的に呼ぶ**（コミット後の呼び出しは応答に出ないため） |

届いたことと、送信の失敗時の挙動は確かめられない。**保留に起こす。**

#### 同じ判定を複数のCommandに持つとき

起動時の判定と実行時の判定で同じ規則を使うことがある。ScriptingCommandは定義単位で独立して
実行されるため、判定の関数も**各Commandが同じものを持つ**ことになる。

**片方だけ直すと、起動情報が「できる」と言った直後に実行が「できない」で落ちる。** 重複を許すなら、
**投入前に2つを機械で突き合わせる**（判定の順序・条件・除去の仕方）。目で見て同じだと思うのでは足りない。

## 11. ホーム（トップView）のパーツへ検索結果の一覧を埋め込む

SFのタブバーのように「タブを押すとその場に一覧が出る」形を、MDCのトップViewのパーツ（GroovyTemplate）で作るときの規則。画面遷移させずに一覧を出すのが目的で、検索画面そのものを枠（iframe）で読み込む形は採らない（ヘッダが重複し、高さが決まらない）。

### 11.1 列は検索Viewの定義から採る

**表示する列を手で書き写さない。** 一覧の列は `MdcEntityViewControlDefinition` の `searchView.searchResultSection.elements`（`type` が `RESULT_PROPERTY` の要素）を**定義順に**読んで決める。こうすると検索Viewを直したときに埋め込んだ一覧も追随し、二重に持たなくなる。View定義の名前は **Entity名のドットをスラッシュへ置いたもの＋View名**。

| 採る値 | 出所 | 注意 |
|---|---|---|
| 列の並びと対象 | `searchResultSection.elements` | `dispFlag` が `false` の要素と多重度が1でない要素は飛ばす。横に溢れるので**上限件数を決めて打ち切る** |
| 列の見出し | 要素の `displayLabel`。空ならEntity定義のプロパティの `displayName` | どちらも空ならプロパティ名 |
| 参照プロパティの値 | EQLで `<プロパティ>.<表示名のプロパティ>` を選ぶ | プロパティ名のまま選ぶとEntityが返り、表に出せない。型は `PropertyDefinitionType.REFERENCE` で判定する。**表示名の在処は参照先によって違う**ので、参照先のEntity定義を見て `Name` か `name` かを決める（§3。決めずに `Name` 固定にすると `not define property` で一覧ごと落ちる） |

総件数は `EntityManager#count(Query)` に**limitを付けない検索**を渡して採る（`select count(oid) ...` を投げると結果が1行なので常に1になる）。

### 11.2 一覧はタブを押したときに読む

パーツを描く時点で全タブ分の一覧を引かない（タブはEntityの数だけ並ぶ）。パネルへ受け皿の要素と対象（Entity名・View名）を属性で持たせ、**タブを選んだときにAPIを1本叩いて描く**。同じパネルを2度読まないよう、読み込み済みの印を受け皿へ付ける。読み込み中・0件・失敗の3つの表示を必ず用意する（§3の「キーが無い＝null」と同じ理由）。

一覧に絞り込みを付けるなら、**検索窓は一覧の右上**に置き、打ってから少し待って（数百ms）読み直す（1文字ごとにAPIを叩かない）。絞った後の件数を出し、空にしたら元の並びへ戻す。**検索語はワイルドカード文字（`%` `_`）と引用符を落としてから渡す**（EQLの文字列に載せる作りだと、前方一致が広域一致に化ける。§3）。手でAPIを叩いて確かめるときは、日本語の検索語を**URLエンコードする**（生のまま置くとHTTP 400で、原因が検索の実装に見える）。

**導線を差し替えるときは、その導線しか持たないタブを空にしないか数える。** 一覧を出すタブでは「一覧を開く」リンクは要らなくなるが、一覧を持たない種別のタブ（Actionを開くだけのタブ等）はそのリンクが唯一の導線で、一律に外すとタブが空になる。

行から先へ進む導線は、**そのホームに既にある導線へ合わせる**。詳細をモーダルで開く仕掛けがホームに無ければ、行は詳細画面へのリンクにする（一覧の表示自体は遷移なしなので目的は満たせる）。モーダル化は別作りになるため、要件なら段を分ける。

### 11.3 横展開は「出すタブ」の指定を1箇所に持つ

最初は1タブで見た目を確かめ、そのあと横へ広げる。**一覧を出すタブの指定はテンプレート内の1つのリストに集め**、`<Entity名>|<View名>` のような、タブを一意に決めるキーで持つ（同じEntityに別Viewのタブが並ぶため、Entity名だけでは足りない）。

**全部へ広げるときは、キーを並べるのではなく種別（ENTITYのタブ）で判定に変える。**列はViewの定義から採るので、タブごとの設定は要らない。広げた直後は**全タブを一度開いて、失敗しているタブを数える**（1タブで確かめた形が他のEntityでそのまま通るとは限らない。実際にToDoと社員カルテが参照先の表示名の違いで落ちた）。

広げる前に、次を1タブで確かめておく。

| 確かめること | 見方 |
|---|---|
| 列が検索画面と同じか | 検索画面を開いて見出しを突き合わせる |
| 参照列に値が出るか | 空欄なら、データが空なのか `.Name` を選べていないのかを分けて見る |
| 総件数が正しいか | limitを変えても件数が動かないことを見る |

投入はホーム全体を差し替えることになるので、**別名トップViewでのコンパイル確認を挟む**（手順は `docs/` の申し送りが定義位置）。

### 11.4 中身のないタブを先頭に置く

SFのホームタブのように、**何も表示しないタブを先頭に置いて最初に開く**形にすることがある。タブの種別を1つ増やして、そのパネルだけ何も描かない分岐にする（一覧の対象からも外す）。

**利用者の設定を「番号」で覚えていると、先頭にタブを足した瞬間に全員の保存値が1つずれる。** タブの選択状態・並び・既定タブを `localStorage` へ持つなら**キーで持つ**。番号で持っているものが既にあるなら、タブを足す前に**キーへ直すか、用途が無くなるなら撤去する**（ずれは「意図しないタブが開く」形で出るので、原因に辿り着きにくい）。

先頭固定にするときは、**動かせる対象から外す場所を数え落とさない**。並びを当てる処理・並びを覚える処理・並び替えの一覧・移動の操作・溢れの畳み込みの5か所すべてで外す（1つ残すと、そこからだけ動いて先頭でなくなる）。

「最初に開くタブ」を変えるときは、**利用者が既定タブを選べる機能があるならそちらを優先する**（固定タブで上書きすると、その機能が黙って効かなくなる）。

### 11.5 タブの状態で他のパーツを出し入れする

「このタブのときだけ他のパーツを見せる」を作るとき、**タブの状態はタブを描いたパーツの中にしかない**。切り替えはそのパーツ側から行い、相手のパーツの定義には手を入れない（戻すのが1パーツの差し替えで済む）。

トップViewのパーツは**同じ行の兄弟セル**に描かれる。相手のパーツのルート要素を掴んだら、**行の直下の子（＝列）まで遡って、その列を出し入れする**。中身だけ隠すと余白と枠が残る。

| 踏まえること | 対処 |
|---|---|
| 列に付くフレームワークのクラスが `[hidden]` に勝つ | `style.display` を直接触る |
| 画面が描き直されると当てた分が戻る | 行に `MutationObserver`（`childList`）を付けて当て直す |
| 相手のパーツがまだ描かれていないことがある | 見つからなければ何もしない。当て直しの機会を持たせる（上の監視で足りる） |

相手のパーツを掴む目印は、**自分たちが書いたテンプレートのルート要素のクラス**にする。製品側のクラスやセルの並び順（何番目の列か）に頼ると、パーツを足し引きしたときに黙って外れる。

### 11.6 一覧の行から詳細をダイアログで開く

ホームの一覧から詳細画面へ**遷移させると、戻ったときにそのEntityの検索画面が空で開く**（検索が実行されないため）。元の画面を残したいときは、**製品の詳細ダイアログを呼ぶ**。自前のモーダルを作る必要はない。

呼ぶ道は次のとおり。パーツは `templateInterpretType` を `VUE_SFC` にすると**Vue SFCとして書け、`iplass-mdc` から製品のコンポーネントを import できる**（画面には製品のエクスポートが載っている）。

| 段 | やること |
|---|---|
| ダイアログの置き場 | SFCのパーツを1つ足し、`MDetailDialog` を置く。開くまで何も描かない |
| 開く | 製品の検索結果と同じ順で呼ぶ: 実行モード（表示なら `VIEW`）→ `viewKey`（`{entityName, viewName}`）→ `entityKey`（`{oid, version}`）→ バージョン指定→ 編集キャンセル時に閉じるか → `open()` |
| 閉じる | **`close:dialog` は「押された」ことを知らせるだけ。親で受けて `close()` を呼ぶ**。受けないと中身だけ消えて枠が残る |
| HTMLのパーツから呼ぶ | SFC側がマウント時に呼び口を1つ `window` へ出し、HTML側はそれがあればクリックを飲み込む。**無ければ従来の遷移に倒す**（SFCが読めなくてもリンクが死なない） |

**SFCのパーツで気をつけること。**

- **非同期にマウントされる。** マウント後の要素を前提にした処理（列を畳む等）は、現れるまで当て直す。行の直下だけを見る監視では拾えない
- **ブラウザ側でコンパイルされる。** 投入前のGroovyTemplateの検査は通ってしまうので、中身の誤りは画面で確かめる（読めないときは製品が警告の枠を出す）
- パーツの列には余白が付く。見せないパーツは**自前のクラスで包んで列ごと畳む**（§11.5）。ダイアログ自体はVuetifyが画面直下へ出すので、列を畳んでも開く

**製品のダイアログは中ほどまでスクロールした位置で開く。** 製品の検索画面から開いても同じなので、こちらの作りを疑う前に製品の画面で同じ操作をして比べる。原因は**大量データ参照セクションが読み込み終わりに自分を `scrollIntoView` する**ことで、セクションの数だけ後から動かされる。

先頭で開かせるなら、**1回戻すのでは足りない**。開いた直後から数秒のあいだ、ダイアログの中のスクロールする要素を繰り返し先頭へ戻す。**その間に利用者がスクロールしたら手を引く**（ホイール・タッチ・キーを見る）。戻し続ける処理は閉じたときとパーツが外れるときに必ず止める。

### 11.7 製品の検索Viewをホームのパーツへ載せる

一覧に「新規・フィルター・行ごとの編集と削除・一括編集」が要ると分かったら、**自前の表を育てる前に製品の検索View（`MSearchView`）を載せられるか確かめる**。必要な引数は `viewKey`（`{entityName, viewName}`）だけで、`queryParameter`（`es=t` 等）を渡すとURLのクエリは見ない。検索条件・新規・行ごとの操作・ページング・表示形式の切り替えは製品の実装がそのまま動く。

| 段 | やること |
|---|---|
| 置き場 | SFCのパーツを1つ足し、`MSearchView` を**1つだけ**描く（タブの数だけ持たない） |
| 対象の渡し方 | HTMLのパーツから `window` の受け口へ「Entity名・View名・描画先の器のid」を渡す。対象が無いときは消す受け口も用意する |
| 描画先 | 器のDOMへ Vue の `Teleport` で描き込む。**SFCパーツ自身の列は畳む**（§11.5） |
| 作り直し | `:key` を「Entity名+View名」にして、対象が変わったら作り直す（前の対象の状態を持ち越さない） |

**ボタンの表示はView定義で決まる。**一括更新は「更新権限 ∧ `searchView.buttonConfig.bulkUpdateButtonConfig.display`」で判定される。`buttonConfig` が無い定義では出ない（`searchResultSection.useBulkView` も併せて見る）。**出ないものは画面側で足さず、View定義を直す。**

| 踏まえること | 対処 |
|---|---|
| 描画に時間がかかるEntityがある | 数秒待つ。待ちが短いと「描かれない」と誤判定する |
| 素早く対象を切り替えると製品側がコンソールエラーを出す | 読み込み中にコンポーネントが捨てられるため（`isSuccessResult` が null）。表示は壊れない。切り替えを遅らせるなら受け口の呼び出しを数百ms待たせる |
| 自前の一覧を撤去する順 | **製品の検索Viewが実機で出ることを確認してから**、自前の表・API・道具を消す。先に消すと戻す先が無くなる |
