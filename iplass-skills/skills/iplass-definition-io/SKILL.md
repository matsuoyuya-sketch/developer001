# iPLAss定義の取得・編集

Entity定義・SelectValue定義・View等をCRUDする共通の規約(パス規約・`@class`・型セグメント・JSON形状)の一次情報は`iplass-dev:iplass-metadata`等のプラグインスキルが担う。本スキルは、この環境でそれらの定義を安全に取得・書き込みするための実務上の要点(経路選択・書き込み規則・サイズ対策・安全策)をまとめる。

環境固有の値(ラッパーの実体パス・Entityパッケージ名・認証用の環境変数・MCPサーバ名)は[CLAUDE.md](../../../CLAUDE.md)の固有値表を参照する。

## 1. 経路の選択

定義を扱う経路は2つあり、扱うJSON形状(型・属性のマッピング)は経路によらず同一。違うのは送受信の手段と応答の包み方だけ。

| 場面 | 経路 | 理由 |
|---|---|---|
| 取得・照合(サイズ問わず) | 定義API | 応答をファイルへ直接落とせるためコンテキストを消費しない |
| 更新(定義全体が大きい) | 定義API | payloadをファイルから送るため出力トークン上限に当たらない |
| 更新(定義全体が小さい) | どちらでも | MCPは1回の呼び出しで完結し手数が少ない |

取得・照合は常に定義APIを使う。更新も定義APIを基本とし、定義全体が小さいときだけMCPでもよい。**判断軸は「変更の大きさ」ではなく「定義全体のサイズ」**である。更新は経路を問わず全置換なので、1項目だけ変える場合でも定義全体を送ることになり、送る定義のサイズで経路を選ぶ。

## 2. 定義API

定義APIを使うには、ラッパー(`<定義APIラッパー>`)が接続の4点セット(社内プロキシ・自己署名証明書・`X-Requested-With`ヘッダ・`Authorization: Bearer`)を隠蔽する。トークンはコマンドライン引数に載せず標準入力から渡す作りにする。事前に認証トークン用・プロキシ用の環境変数(値はCLAUDE.md参照)が必要で、未設定ならラッパーは終了コード2で起動時に止まる。

| サブコマンド | 相当するMCPツール | 用途 |
|---|---|---|
| `get <path> [出力ファイル]` | `getDefinition` | 定義取得。出力ファイル省略時は標準出力 |
| `list <path末尾/> [出力ファイル]` | `getDefinition`(一覧) | 一覧取得(再帰指定可) |
| `post <path> <payload.json>` | `createDefinition` | 新規作成 |
| `put <path> <payload.json>` | `updateDefinition` | 更新(全置換) |
| `delete <path>` | `deleteDefinition` | 削除 |

例: `<定義APIラッパー> get /entity/<パッケージ>/<Entity名> <保存先ファイル>`

素のHTTPで叩く場合の要点:

- ボディは**定義オブジェクトそのまま**。`{"definition":{...}}`でラップすると400、form-urlencodedの`definition=<json>`は415になる。
- `X-Requested-With: XMLHttpRequest`欠落で500(`Content-Length:0`・body無し)になる。認証の有無に関わらず同じ500になり原因が見えにくいので、500を見たら真っ先にこのヘッダを疑う。
- `Authorization: Bearer`欠落/不正は401になる。
- 応答の`.definition`は**オブジェクト**(パースは1回で済む)。
- 存在しないパスでも200`{"status":"SUCCESS"}`(definitionキー無し)が返る。不在の判定・削除の確認は`list`の一覧で行う。
- 定義APIはAdminConsole側でメソッドごとのWebApi定義として公開されているため、事前に`enableDefinitionApi`を有効にしておく必要がある。GET用の定義はトークンチェックを不要にしておく(有効なままだと`X-Transaction-Token`ヘッダが別途必要になる)。

## 3. MCP

ツール名は`mcp__<MCPサーバ名>__<操作>`の形式。使う前に`ToolSearch`で対象サーバのツールスキーマを読み込む。

| ツール | 引数 | 用途・戻り |
|---|---|---|
| `getDefinition` | `{path}` | 取得。末尾`/`なら一覧、それ以外なら定義本体。`recursive:"true"`で階層取得 |
| `createDefinition` | `{path, definition}` | 新規登録。`definition`はJSONオブジェクト |
| `updateDefinition` | `{path, definition}` | 更新(全置換。差分ではない) |
| `deleteDefinition` | `{path}` | 削除 |

`getDefinition`の応答の`.definition`は**JSON文字列**なのでparseしてから中身を参照する。書き込み時は逆にオブジェクトで渡す非対称な作りで、定義APIの応答(オブジェクト)とはこの点だけ違う。`update`/`create`/`delete`はスラッシュ形式パスが必須(ドット形式は`-32603`エラーになる)。`get`の詳細取得はドット形式も通る。応答が会話コンテキストに入るため、大きな定義の取得・全置換更新は出力上限に当たりやすい(§8)。MCPでは書けない定義がある(`-32603`)。その場合はAdminConsoleのXMLインポートへ回す。

**先頭の`/`も必須**: パスの先頭に`/`を付けないと、存在しないパスと区別できない200`{"status":"SUCCESS"}`(definitionキー無し)が返る(§2の「存在しないパスでも200 SUCCESSが返る」と同じ症状がMCPでも起きる)。`get`/`list`/`update`/`create`/`delete`のいずれも先頭`/`付きのパス(例`/entity/...`)で呼ぶ。

## 4. 書き込み規則

**パス**: Entityは`/entity/<ドット区切りの定義名をスラッシュに展開したパス>`になる。例: 定義名`foo.bar.Sample` → パス`/entity/foo/bar/Sample`。

定義には項目配列が2つある。

- `propertyList` — システム項目＋宣言項目をマージした一覧(読み取り用の表現)
- `declaredPropertyList` — 自分で宣言した項目のみ

**書き込み時の原則**: 全置換(`put`)は`propertyList`だけを読む。`declaredPropertyList`はリクエストでは読まれない(GET応答に載る派生表示にすぎない)。したがって項目の追加・変更・削除は必ず`propertyList`に反映する。ペイロードに`propertyList`キー自体が無いと、`declaredPropertyList`に入れて送っても`{"status":"SUCCESS"}`を返す一方で全項目が保存されず、システム項目だけの空Entityになる。

取得結果を土台にする通常の更新(ペイロードに両方のキーが残る)でも、この原則は変わらない。追加・変更を`declaredPropertyList`にだけ反映し`propertyList`側を更新し忘れると、`{"status":"SUCCESS"}`を返しつつその追加・変更は無視され、取得し直すと元のままに戻る。定義直下の属性(`description`等)の変更はこの影響を受けず反映される。追加するプロパティは、両リストの末尾にそれぞれ独立したコピーを入れておく。`declaredPropertyList`側は書き込み時にサーバから読まれないが、次回GET応答で`propertyList`と`declaredPropertyList`を照合するときに食い違いが出ないよう揃えておく(読まれない=省略してよい、ではない)。`propertyList`は継承プロパティ(`oid`・`name`・`updateDate`等、`inherited:true`が付く)を含む実効一覧なので、件数は常に`declaredPropertyList`より多い。

**照合の原則**: `{"status":"SUCCESS"}`は保存の証拠にならない。作成/更新のたびに取得し直し、`propertyList`と`declaredPropertyList`の両方について、件数だけでなくプロパティ名の集合が送った内容と一致するか確認する(件数だけの照合では、片方のリストへの反映漏れを見逃す)。削除も同様で、削除後の取得は200 SUCCESSを返すだけなので一覧で消滅を確認する。

**送信内容との一致だけを基準にしてはいけない。** 送信内容そのものが壊れていた場合、保存結果と送信内容は一致するので照合を通ってしまう。ペイロードを生成して投入するときは、基準に**意図した内容**も含める。長い本文(スクリプト・テンプレート・SFC)は正本をファイルに置き、投入前に「その本文が必要な要素を保持しているか」を機械で検査し、投入後は**そのファイルと突き合わせる**。

**システム項目**: 全Entityに`oid, name, description, version, state, startDate, endDate, createDate, updateDate, createBy, updateBy, lockedBy`の12項目が自動付与される(`propertyList`では`inherited:true`が付いて現れる)。**新規作成**では自分で宣言する項目だけを送り、この12項目は`propertyList`に含めない(サーバが自動でマージする)。**取得結果を土台にする更新**では、取得した`propertyList`にこの12項目が既に載っているので、そのまま残す(削除・改変しない。前段のとおり`propertyList`は継承プロパティ込みの実効一覧なので、更新時に毎回この12項目を除く必要はない)。移行元でオーナー参照のような項目(例: `OwnerId`)がこの12項目に含まれない場合は、通常項目として扱う。

**取得結果をそのまま再送できる要素**: `eventListenerList` / `storeDefinition` / `versionControlType`等のトップレベル要素は、取得した値をそのまま載せて送れば保持される。

**フィールド名は資料より実物に合わせる**: boolean項目の名前は`is`接頭辞の付かない形(`checkXRequestedWithHeader` / `privileged` / `publicWebApi`等)である。存在しない名前で送ると`{"status":"SUCCESS"}`を返しながらその項目だけ黙って捨てられる。`iplass-dev`プラグインのスキルの表記と実物が食い違うことがあるため、**同種の動いている定義を1つ取得してフィールド名と値を写す**。投入後は取得し直して当該項目が保存されているかを見る。

**写す実物が無いフィールド名は、AdminConsoleで1件だけ設定してもらってから読む。** 未設定のフィールドは定義のJSONに現れないため名前が分からない。開発ガイドは設定項目の**日本語ラベル**しか載せておらず、MDC系は公開Javadocにも公開OSSリポジトリにも無い(EEモジュール)。**候補名を送って生き残りを見る探索は、入れ子のオブジェクトでは`@class`と内部のフィールド名も当てる必要があるため現実的でない**(未知のキーは黙って捨てられるので定義は壊れないが、当たらない)。GUIで仮の値を1件保存してもらい、定義を取得してキー名・クラス名・フィールド名をまとめて採るのが最短。AdminConsoleの画面上の場所は開発ガイドの図に頼る(図はダウンロードして見る。文章だけでは特定できない)。

**空の配列は応答からキーごと落ちる。** 配列を空にして送る更新（ボタンをすべて外す等）は、取得し直すとそのキーが無い状態で返る。照合するコードが要素数を数える形だと、キーが無いところで止まる。**「キーが無い＝空」**として読む。

**Entity以外の定義の照合**: 項目配列を持たない定義(WebApi・Command・View等)は件数照合ができない。投入した中身が長い文字列(スクリプト本文等)なら、取得結果と送信内容が完全一致するかを比較する。

**スクリプトで解決できないimportがある**: `groovy.json`(JsonSlurper等)はimportした時点で**クラスのロードごと失敗**し、`execute`をtry/catchで囲んでも捕まえられない500になる。原因が見えない500に当たったら、まず`org.iplass.*`以外のimportを疑って外す。JSONの解釈が必要なときは、サーバが持つJacksonの`com.fasterxml.jackson.databind.ObjectMapper`を使う。

**リクエストボディのJSONは`getParam`で取れない**: WebApi定義で`accepts`に`REST_JSON`を指定し`restJsonParameterName`を設定しても、Command側の`getParam`はnullを返す。**`accepts`は`REST_FORM`にし、JSON文字列を1つのパラメータとして送ってCommand内で解釈する**のが確実。呼び出し側は`Content-Type: application/x-www-form-urlencoded`でボディをURLエンコードして送る。

**スクリプト実装のCommandとテンプレート定義は、更新が実行に反映されないことがある**: 通常は同名`put`で反映される。ただし保存された新しい内容と実行される内容が食い違い続ける状態に陥ることがあり、そのとき`delete`→`post`や`newInstancePerRequest`では戻らない。取得して保存を照合しても差は出ないため、**変更したはずの挙動が変わらない**という形でしか気づけない。テンプレート定義(Vue SFC等)でも起きるので、画面の見た目が変わらないときはこれを疑う。

対処は次の順で試す。

| 手順 | 内容 |
|---|---|
| 反映の確認 | スクリプトのレスポンスへ版を示す値(`marker: 'v2'`等)を仕込み、呼び出して値が変わったかで判定する。**保存内容の照合では分からない** |
| 1 | 同名で`put`する |
| 2 | 参照元(WebApi・ActionMapping等)の定義も`put`し直す |
| 3 | 定義名を変えて作り直し、参照元の`commandName`を差し替える |

**この状態に入ったら手順3へ進む。** 手順1・2は戻らないことがある(`delete`→`post`も同じ)。
手順2で参照元の`put`が500になることもあり、その場合は参照元も作り直す側へ回す。
**変更が頻繁に入る部分はスクリプトCommandに置かない**のが根本の対処で、テンプレート定義の
本文へ寄せられるものは寄せる(この症状が出ないため、名前を変えずに反復できる)。

テンプレート・スクリプトセクション側にはこの症状は出ない。

書き込みの鉄則の本体はこの節と§5であり、他のスキル・リファレンスでは繰り返さない。送信直前にliveを取得し投入予定JSONとdiffを取ること(drift対策)は全経路・全更新で必須で、詳しい手順は§5にまとめる。

## 5. 取得 → 編集 → 投入 → 照合

前提: 投入する定義(項目配列を持つJSON)が手元にある。対象のEntity・パッケージを変えても同じ手順が使える。

以下は定義APIの表記(get/post/put/delete)で書く。MCPを使う場合はget→getDefinition / post→createDefinition / put→updateDefinition / delete→deleteDefinitionと読み替える。手順自体は同じ。

1. **既存確認**: `get`で取得する。既に項目付きで存在するなら以降は`put`を使い、未存在なら`post`を使う。存在しないパスでも200 SUCCESSが返るので、不在の判定は`list`の一覧で行う。
2. **drift確認(更新時は必須)**: 手順1で取得したliveと、投入予定のJSONをdiffする。全置換なので、他者が直接触った変更を黙って踏み潰してしまう。差分があれば内容を確認してから進める。
3. **新規SelectValue定義を先に投入**: Entityが新規のSelectValue定義を参照している場合は、Entityより先にSelectValue定義を投入する。
4. **登録/更新**: 新規は`post`、更新は`put`。payloadは定義オブジェクトそのまま。項目は`propertyList`に入れる。トップレベルには`@class`/`name`/`displayName`/`versionControlType`/`storeDefinition`を付ける。
5. **照合(検証ゲート・必須)**: `get`で取得し直し、§4の照合の原則に従って`propertyList`と`declaredPropertyList`の両方をプロパティ名の集合で照合する。SUCCESSだけでは保存された証拠にならない。不一致(特に0)の場合は送信フィールドが`propertyList`になっているか確認する。

削除の確認も同じ考え方で行う。削除後の取得は200 SUCCESSを返すだけなので、一覧取得で対象が消えたことを確認する。

## 6. HTTPステータス別の原因

定義APIを素のHTTPで扱うときの症状は、次の対応でほぼ説明できる。

| 症状 | 原因 |
|---|---|
| 500(`Content-Length:0`・body無し) | `X-Requested-With: XMLHttpRequest`ヘッダ欠落。認証の有無に関わらず同じ500になる |
| 401 | `Authorization: Bearer`ヘッダの欠落または不正 |
| 415 | Content-Typeがform-urlencodedになっている(生JSONで送る) |
| 400 | ボディを`{"definition":{...}}`でラップしている(定義オブジェクトそのままを送る) |
| 400(**bodyが空**) | 入れ子のオブジェクトに`@class`が無い。多言語の要素(`localizedDisplayLabelList`等)は`org.iplass.mtp.definition.LocalizedStringDefinition`が必要で、無いと**理由が一切返らない**。切り分けは要素を減らしながら投入して当たりを付ける(セクション0件は通るのにセクション1件で400なら、そのセクション配下の入れ子を疑う) |
| 未知のキーを送っても通る | 仕様。**受理されずに黙って落ちる**ため、キーの有無を「投入できたか」で探ることはできない。投入後に`get`して残っているかを見る |
| 削除後の`get`が200 SUCCESS | 仕様。不在の確認は一覧取得で行う |

`@class`が要るのは抽象型の入れ子だけではない。**具象型しか入らないリストの要素でも要ることがある**
(ワークフロー定義の`variableList`の要素は `org.iplass.mtp.workflow.definition.VariableItem` が必要で、
無いと400になる)。400を見たら、入れ子の要素すべてに`@class`を付けて切り分ける。

**ScriptingCommandを同じ名前で更新しても、実行されるのは古いスクリプトのまま。**
`put`は200を返し、`get`でも新しいスクリプトが返るのに、**呼び出すと更新前の挙動をする**
(コンパイル済みスクリプトが定義名で握られている)。`newInstancePerRequest`をtrueにしても変わらない。
**回避は別の定義名で作り直すこと**(`...CommandV2`のように版を上げ、参照側も差し替え、旧名を削除する)。
切り分け方: スクリプトに版の目印を出力させ、呼び出して目印が変わるかを見る。変わらなければキャッシュ。
**この症状は「投入は成功しているのに直したはずの不具合が再現する」形で現れる**ので、
スクリプトを直したのに挙動が変わらないときは、まずこれを疑う。

**定義の名前に階層(ドット)を許すかは種別による。** Entityやテンプレートは `mtp.bussiness.X` のように
階層を持てるが、**ワークフロー定義は平坦な名前でなければならない**。階層のある名前で投入すると
内容が正しくてもHTTP 500(`WebApiRuntimeException`)になり、応答からは名前が原因だと分からない。
**内容の切り分けで原因が出ないときは、名前を平坦にして試す。**

自作したWebApiを同じトークンで呼ぶときは、定義側の設定不足も同じHTTPエラーとして現れる。

| 症状 | 原因 |
|---|---|
| 403 `NoPermissionException` | WebApi定義の`supportBearerToken`が未設定。Bearerトークンで認証されずゲストとして実行されている |
| 415 | WebApi定義の`accepts`と送信Content-Typeの不一致。クエリパラメータで受けるなら`accepts`は`REST_FORM`にし、`GET`では`Content-Type`を送らない |
| 500(bodyなし) | 上記2つのいずれか。`accepts`が`REST_FORM`のとき、`POST`は`Content-Type: application/x-www-form-urlencoded`で送る |

## 7. 扱えるメタデータとパス

パスは末尾が`/`なら一覧、それ以外なら本体を指す。

| メタデータ種別 | パス接頭辞 | 定義名の区切り | AdminConsoleでの場所 |
|---|---|---|---|
| Entity定義 | `/entity/` | パスはスラッシュ、定義名はドット | `Data Model` > `Entity` |
| SelectValue定義 | `/property/select/` | スラッシュ | `Data Model` > `SelectValue` |
| WebApi定義 | `/webapi/` | スラッシュ | `Customization` > `WebApi` |
| Template定義 | `/template/` | スラッシュ | `Customization` > `Template` |
| Command定義(Java実装・スクリプト実装の共通) | `/commandClass/` | スラッシュ | `Customization` > `Command` |
| MDC系のEntity画面定義 | `/view/mdc/entityview/` | `<Entity名をスラッシュ展開>/<View名>` | `Data Model` > `Entity` > 対象Entityを右クリック > `MDC EntityView` |
| メールのテンプレート定義 | `/mail/template/` | スラッシュ | `System` > 通知系 |
| SMSのテンプレート定義 | `/sms/template/` | スラッシュ | 同 |
| プッシュ通知のテンプレート定義 | `/pushNotification/template/` | スラッシュ | 同 |
| テナント設定 | `/tenant/` | 定義名は `Tenant` の1件 | `Tenant` |

定義名のスラッシュはAdminConsoleのツリー上でフォルダの入れ子として現れる。

宣言的画面には系統が2つあり、業務画面がMDC系のときGEM系(`/view/generic/`)には定義が存在しない。**GEM系に無いことは「画面定義が無い」ことを意味しない。** どちらの系統かは両方の一覧を取って判断する。

一覧取得できない例外がある: ルート(`/`)・空文字・`/view/`・`/view/mdc/`・`/menu/`等。接頭辞は正確な文字列でないとサーバ例外になり、大小文字も厳密に区別される。中間のセグメントでは取れず末端(`/view/generic/`・`/view/mdc/entityview/`)で取れる。

**接頭辞は複数のセグメントを持つことがある。** 通知系は`/mail/template/`のように2段で、
**1段目(`/mail/`)ではサーバ例外になる。** 種別が無いのか接頭辞が浅いのかは、**どちらも同じ
HTTP 500 + `WebApiRuntimeException`で返るため応答からは区別できない。**

未知の種別を扱うときは、上表の既知の接頭辞から試す。それでも当たらないなら、**接頭辞を推測で
足し続けない。** 定義の型名(`...Definition`)と型セグメントの対応は `iplass-dev:iplass-metadata`
のルーティングマップが定義位置で、そこを引けば1回で分かる。

**mdc Viewのパス**: 種別ごとに階層が分かれる。EntityViewだけはEntity名の後ろに**View名**が付く(既定は`DEFAULT`)。Entity名はEntityのパスと同じくドット区切りをスラッシュに展開する。

| 種別 | パス |
|---|---|
| 詳細View・検索View(EntityView) | `/view/mdc/entityview/<Entity定義名をスラッシュに展開したパス>/<View名>` |
| サイドメニューのitem | `/view/mdc/sidemenu/item/<名前>` |
| ナビゲーション(SideMenuTree) | `/view/mdc/navigation/<名前>` |
| トップ画面(TopView) | `/view/mdc/topview/<名前>`(既定は`DEFAULT`) |
| スプレッドシート(SpreadSheet) | `/view/mdc/spreadsheet/<名前>` |

**上表に無い種別のパスを探すときは、一覧の応答で当たりを判断しない。** 種別が違うパスでも`{"status":"SUCCESS","list":[]}`が返り(§2の「存在しなくても200」と同じ)、定義が0件なのか種別を外したのか区別できない。**本体をGETして`@class`が返ることで確定する。** 接頭辞そのものが違うときはHTTP 500になる。

一覧は`/view/`直下では取れないので、上表の種別ごとの階層まで下りて指定する(`/view/mdc/entityview/`・`/view/mdc/sidemenu/item/`)。**`/view/mdc/`と`/view/mdc/sidemenu/`はHTTP 500になる**ので、500を見たら一覧の階層が浅くないかを疑う。

MCPでは大きい定義(200KB超)は応答が別ファイルに退避される。定義APIならgetの出力先ファイルを指定すればそのまま落ちる。いずれの経路でも、保存されたことの確認は`propertyList`/`declaredPropertyList`の件数照合で行う。

## 8. 送信サイズの上限と縮小

更新は全置換かつ不可分(分割送信不可)。送信を阻む上限は2種類あり、区別して考える。

1. **定義/メッセージのサイズ上限** — 数百値の選択肢を多数インラインで持つと定義が増大し超過しやすい。
2. **モデルのツール呼び出し1回あたりの出力トークン上限** — 全置換は不可分なので、完全な定義がこの上限を超えると送れない。

**(2)は定義APIを使えば発生しない**: payloadをファイルから送るため、定義がアシスタント出力に乗らない。大きな定義の更新は定義API経路を選べば、下記の縮小手当てが丸ごと不要になる。

**MCPで更新する場合のみ(2)が問題になる**。対処の順序:

1. **第一手(短縮より先に行う)**: 取得結果は、参照付き(SelectValue定義参照)のSelectPropertyにも解決済みの選択肢一覧を冗長にインライン同梱している。全置換更新で再送する際は、この参照付きSelectの冗長なインライン選択肢を送信前に削除し、参照名だけ残す(サーバ側でSelectValue定義から解決される)。事前に参照先のSelectValue定義が実在することを確認する。
2. **それでも収まらない場合のみ**: 真にインラインのみの大きな選択肢を、共通のSelectValue定義(Global)へ切り出して参照に変える。送信データは最小化(minify)する。

短縮は最後の手段であり、**短縮した事実と対象フィールドを必ず報告する**。無断で短縮しない。大きな定義の全置換更新は、まず定義API経路を検討する。

## 9. 全置換更新の安全策

経路に関わらず、全置換前に元定義(取得結果)をファイルに保存しておく(破損時の復旧元)。定義APIならgetの出力先をそのまま保存先にできる。

一部の属性だけ変える更新は手書きせず、元定義をプログラムで読み対象キーだけ書き換え、他はバイト同一を保つのが安全。定義APIなら「取得→加工→送信」が全部ファイルで繋がるので、この流れが自然に成立する。

**`${...}`やバックスラッシュを含む本文を、シェルを経由して組み立てない。** GroovyTemplateの埋め込み(`${変数}`)・正規表現(`[\s\S]`)・SFCはこれらを字面として保持する必要があるが、シェルの展開やエスケープの段数で静かに潰れる(`${contractOid}`が空文字になる、`[\\s\\S]`が`[sS]`になる)。**投入も検査も通るのに実行時だけ壊れる**ため、原因が見えにくい。本文はファイルへ直接書き、ペイロードにはそのファイルを読み込んで載せる。

MCPで往復する場合のみ、巨大な取得応答はharnessが自動保存するファイルを照合スクリプトへ直接渡す(往復のたびに全文を出力し直さない)。

## 10. 型・索引変更の in-place 可否

| 変更 | in-place可否 | 理由 |
|---|---|---|
| String→LongText | 可 | 値の持ち方が同じで、データを引き継いで変換できる |
| indexType付与(例: UNIQUE) | 可 | 索引の追加だけで値に触れない(更新中はデータにレコードロックが掛かる) |
| displayName・選択肢の値/表示名の変更 | 可 | 格納構造に影響しない |
| 多値↔単値の変更 | 不可 | **多重度が1以外のプロパティは単値と別の格納(多値用ストア)を使う**ため、多重度の変更は格納の作り直しになる。in-place updateでは新しいストアが確保されず`getStore() is null`で失敗する |
| 基本型プロパティ→Referenceプロパティ | 不可 | 値そのものを持つか他Entityへの参照を持つかが別で、値を変換できない(サーバが型変換不可のエラーを返す) |
| String→Expression / Expression→String | 可 | `resultType` と `updatable:false` も保持される。除去→再追加の2段階は要らない |

**プロパティの除去→再追加は、そのEntityを参照しているmdc Viewを読めなくすることがある。** 参照セクションを持つViewが対象になる。この2段階を使うときは、対象EntityのViewを投入し直す前提で計画する(症状と復旧は `converting-salesforce-layout-to-iplass-view` §12)。

in-place updateで適用できる変更でも、ストア構造が変わる変更は失敗し得るため、更新後は必ず取得し直して反映を照合し、画面表示も確認する。不可な変更は次の2段階で行う: ①該当プロパティを一旦除去して更新→②目的の型/多重度で再追加して更新(全置換なので毎回全項目を送る)。

## 11. View全置換と`propertyName`欠落要素

mdc View(詳細View・検索View等)の全置換は、`propertyName`を持たない要素が1件でも含まれるとHTTP 500(`WebApiRuntimeException`系のシステムエラー)になる。エラーメッセージからは原因が特定できない。

`propertyName`を持たない要素(画面上は何も表示しない、画面生成処理が残した要素)は、詳細Viewだけでなく検索Viewの検索条件・検索結果にも出現し得る。**取得した定義を無改変で送り返しても500になることがある**点に注意する。サイズの上限とは無関係で、大きい定義が成功し小さい定義がこの理由で失敗することもある(「サイズ上限」に見えるため、削って回避する方向に時間を使いやすい)。

**切り分け方**: 詳細Viewの要素を1件ずつ増やしながら送信する二分探索で境目を特定する。壊れた要素を含む組は必ず500になり、含まない組は必ず成功する。

**対処**: 全置換の前に、詳細Viewと検索View(検索条件・検索結果の両方)から`propertyName`を持たない要素を除去する。除去は定義の修復にあたるため、**除去した件数を報告する**。`scripts/sf-to-iplass/view/convert.js`の`sanitizeDefinition`がこの除去を担う。

**この除去はView定義専用**である。要素を`propertyName`の有無で判別するため、プロパティを`name`で持つEntity定義に当てると全プロパティが除去対象になる。View以外の定義には使わない。

## 12. 定義のプロパティ仕様をソースから調べる

定義APIは未知のキーを黙って捨てる(§4)ため、キーの名前をプローブで探り当てることはできない。**投入したいキーの名前・許容値・既定値は、iPLAss本体のソースから引く。**

置き場と投入方法(いずれも実体は `CLAUDE.md` の固有値表が定義位置):

| 見たいもの | 置き場 |
|---|---|
| 定義クラス(JSONのキー・許容値)、内部の保存形、管理コンソール側の入力形式 | `<ソース参照ディレクトリ>` のJava側。モジュールごとに `mdc` / `core` / `gem` / `web` / `admin` に分かれる |
| mdc画面のコンポーネント実装(描画と操作の実際)、propsの型 | `<ソース参照ディレクトリ>` のフロント側。`src/main/vue/` に原ソース、`dist/` に型定義 |

**このディレクトリはGit管理外で、各自がローカルへ投入する。** 投入は `scripts/iplass/fetch-reference-sources.sh` を実行する(有償版の資格情報が必要。呼び出し方は `scripts/iplass/README.md`)。無い環境では代わりに同梱の javadoc を見るが、javadoc は公開APIだけで **mdc の定義クラスを含まない**(置き場は `.claude/skills/README.md` の「公式ドキュメント」節)。

**ソースと併せて、同梱の公式ドキュメントも引く。** 役割が違うので片方だけでは足りない。

| 引くもの | 分かること |
|---|---|
| 公式ドキュメント(開発ガイド・service-config・EQLリファレンス。置き場は `.claude/skills/README.md` の「公式ドキュメント」節が定義位置) | **その設定が何をするのか**、種別ごとに用意されている機能の一覧、GUIでの設定項目名、値の意味と使い分け、他の定義との前後関係 |
| ソース | **JSONのキー名・許容値・既定値・ネストの形**(公式ドキュメントには書かれていない) |

**先に公式ドキュメントで機能とGUIの項目名を掴み、次にソースでキーを確定する**方が速い。ソースから入ると、そのキーが何のためにあるのかが分からないまま形だけ写すことになり、関連するキーの取りこぼしにも気づけない。逆に公式ドキュメントだけで進めると、GUIの手順からJSONの形を推測することになる(公式ドキュメントがGUI操作で書かれていることは `.claude/skills/README.md` の「公式ドキュメント」節が定義位置)。

### 12.1 調べる順序

**live の定義をGETして `@class` を読むところから始める。** 定義の種別ごとにクラスが分かれており、`@class` がソースへの唯一の入口になる。公式ドキュメントの画面名やGUIの項目名からクラス名を推測すると外れる。

| 手順 | 見るもの | 得られるもの |
|---|---|---|
| 1 | live定義の `@class` | 調べる対象のクラスの完全修飾名 |
| 2 | `<クラス名>.java` のフィールドとgetter/setter | **JSONのキー名**(getter/setter名がそのままキーになる)とフィールドのコメント |
| 3 | フィールドの初期化子 | **既定値**(`= true`・`= 12`・`= <enum定数>` のように定義クラス側で持つことがある) |
| 4 | `extends` で親クラスを辿る | 継承したキー(子クラスだけ見ると漏れる) |
| 5 | ネストされた `enum`、または同パッケージの `enum` | 文字列キーの**許容値の一覧**。素の `String` で持ち、`enum` が無いこともある(手順7の下を見る) |
| 6 | `impl` 配下の `Meta<クラス名>.java` | 保存形。`applyConfig` / `currentConfig` が定義とメタの写し取りで、**ここに無いフィールドは保存されない** |
| 7 | `@XmlSeeAlso` と `@JsonTypeInfo` | **指定できるサブクラスの一覧**。`@class` が必要かどうかは注釈では判断できず、liveのGET結果に `@class` があるかで決める(注釈が無いクラスでも入る) |
| 8 | `Handler` / `Discloser` の内側 | **そのキーが実際に効く条件**(片方だけ設定すると機能しない、他の定義に値が無いと無視される、等) |
| 9 | フロント側の対応コンポーネントと `dist/` の型定義 | 画面での見え方と、渡せる値の型 |

**設定がネストしたオブジェクトで束ねられている種別がある。** フィールドの型が別の定義クラスなら、そのクラスも手順2以降を同じ順序で辿る。トップレベルのクラスだけ読むとキーの大半を見落とす。

**既定値と管理コンソールのラベルは、定義クラスに無ければ `admin` モジュール側にある。** 置き場は3通りで、この順に当たる。

| 探す先 | 何が入っているか |
|---|---|
| 定義クラスのフィールド初期化子 | 既定値。`@MetaFieldInfo` の `displayName` があればラベルも |
| `impl` 配下の `Meta<クラス名>` | 保存形(既定値は持たないことが多い) |
| `admin` モジュールの画面クラス(`*Form` / `*Item` / `*Grid` 等) | **画面で設定できる既定値**(`setValue(true)`、`getXxx() != null ? … : <既定>` の形)、**`enum` を持たないキーの許容値**(選択肢の一覧として書かれている)、ラベル |

`admin` を引くときは**パスに `mdc` セグメントを含めて絞る**。GEM系とmdc系で同名・同構造の画面クラスが同じ階層に同居しており、種別名だけで探すとGEM系の方を読んでしまう。

注釈の読み分けが2つある。

- **`@Presentational` は「フロントへ渡す属性」の印で、投入できないことを意味しない。** 画面の描画に使う値(CSSクラス名・ラベル・ツールチップ等)にも付いており、これらは投入する側の設定項目である。`@MetaFieldInfo` が併記されていれば管理コンソールで設定できる項目なので、投入して構わない。投入しても意味が無いのは、値がクラス側で固定されているフィールド(種別を表す `type` など)である。
- 種別を表す `type` のように、getter が公開されておらず**JSONのキーとして現れない**フィールドがある。種別の指定は `@class` で行う。

### 12.2 引き方

クラス名・キー名・GUIの項目名のどれからでも入れる。`Grep` はソース参照ディレクトリを `path` に指定して使う。

| 手掛かり | 引き方 |
|---|---|
| live定義の `@class` | 完全修飾名の最後の要素をファイル名として `Glob` で `**/<クラス名>.java` を引く |
| GUIの項目名(公式ドキュメントの手順書に出てくる語) | まず定義クラス側で `@MetaFieldInfo` の `displayName` を語で `Grep` する。当たらなければ `admin` モジュールの画面クラスを同じ語で `Grep` し、その近くで参照しているフィールド名を読む(語で当たらないときは §12.3) |
| JSONのキー名(liveにあるが意味が分からない) | `private .* <キー名>` で `Grep` し、宣言元のクラスを特定する |
| 許容値(文字列でしか見えない値) | その値のリテラルを `Grep` して `enum` の定義に当てる |
| そのキーの効き方 | キー名の getter を `Grep` し、`impl` 配下の呼び出し箇所を読む |
| 画面のどこに出るか | フロント側で対応するコンポーネント名を `Grep` する |
| そのキーが何のためにあるか・関連するキーの取りこぼし | 公式ドキュメントの該当種別の頁を機能名で `Grep` する。**頁が用意されていない種別もある**ので、無ければソースだけで進める |

**Java側とフロント側は別々に取得している**ので、両方を横断して探すときは2回引く。

**GUIの項目名と定義のキー名は一致しないことがある**(画面側の名前がそのままキーになっていない)。GUIの語で当たりを付けたら、必ず定義クラス側のフィールド名を読んでキーを決める。

### 12.3 ソースを見ても分からないこと

| 事柄 | 確かめ方 |
|---|---|
| そのキーを定義APIで投入できるか | ソースにフィールドがあっても、APIの経路が受け付けない・保存されないことがある。投入して取得し直して照合する(§5) |
| 版の差 | ソースの版が環境と一致していることを前提にする。一致しない版を読むと存在しないキーを書く |
| GUIでしか設定できない項目 | §5の照合で保存されないことが分かったら、GUIで設定する旨を残す(書き方は `writing-project-skills/SKILL.md` §11) |
| 管理コンソールのラベルの実際の文字列 | `admin` 側のラベルが多言語化のキー参照(`getString("ui_metadata_...")`)で書かれている種別では、ソースから文字列を取れない(メッセージのファイルはソースに含まれない)。GUIの語からキーを逆引きすることも諦めて、**画面を開いて項目名とキーの対応を確かめる** |
| 値を省略したときの画面の挙動 | 定義クラスと `admin` の両方に既定値が無いキー(`Integer` / `Boolean` のまま初期化されていないもの)は、フロント側の実装で決まる。フロント側のソースを引く(置き場は §12 の表) |
